**Status:** FROZEN  
**Version:** 1.0  
**Date:** March 28, 2026  
**Owner:** Data / Platform Engineering

## 1. Overview

This document defines the canonical telemetry schema for SmartLoad. All telemetry data collected from backend nodes, routing decisions, and system events must conform to this schema. This is the single source of truth for data contracts across all modules (Forecasting, Anomaly Detection, RL, dashboards, and ML pipelines).

**Key principle:** Once this schema is frozen, changes require a major version bump and coordinated migration.

---

## 2. Naming Convention

### 2.1 Hybrid Namespace Format

All telemetry metrics follow the format:

```
smartload.<domain>.<metric_name>
```

**Domain categories:**

| Domain | Purpose | Examples |
|--------|---------|----------|
| `request` | HTTP request handling | `smartload.request.latency`, `smartload.request.count` |
| `error` | Error tracking | `smartload.error.rate`, `smartload.error.count` |
| `backend` | Backend node health | `smartload.backend.cpu`, `smartload.backend.memory` |
| `routing` | Routing decisions | `smartload.routing.decision`, `smartload.routing.score` |
| `scaling` | Autoscaling events | `smartload.scaling.action`, `smartload.scaling.trigger` |
| `system` | Platform-level metrics | `smartload.system.availability`, `smartload.system.queuedepth` |

### 2.2 Metric Naming Rules

- **Lower case with underscores:** `smartload.request.latency_ms` (not latencyMs, latency-ms)
- **Units in suffix:** `_ms` (milliseconds), `_sec` (seconds), `_pct` (percent), `_count` (unitless)
- **No redundancy:** `smartload.request.latency_ms` not `smartload.request.latency_latency`
- **Adjectives optional:** `smartload.backend.cpu_usage` or `smartload.backend.cpu` are both acceptable

## 3. Timestamp Format & Precision

### 3.1 Standard

All timestamps use **ISO 8601 format in UTC with millisecond precision:**

```
YYYY-MM-DDTHH:MM:SS.sssZ
```

**Examples:**
- `2026-03-28T14:23:45.123Z` ✅ Correct
- `2026-03-28T14:23:45Z` ❌ Missing milliseconds
- `2026-03-28T14:23:45.123456Z` ❌ Nanosecond precision (not supported in v1)
- `2026-03-28T14:23:45.123+02:00` ❌ Non-UTC timezone

### 3.2 Enforcement

- **Database layer:** `TIMESTAMPTZ` columns enforce UTC; any input is converted to UTC before storage
- **Collector/Agent layer:** Agents must convert local timestamps to UTC before emission
- **Client layer:** Dashboard and queries must parse all timestamps as UTC

### 3.3 Clock Skew Tolerance

SmartLoad tolerates ±500ms clock skew between backend nodes and the collector. Timestamps deviating >500ms from the collector's local time are logged as warnings but accepted. No data is silently dropped due to clock skew.

## 4. Server Identifier Format

### 4.1 Composite Key

Every telemetry record includes three server identifiers to enable flexible grouping and auditing:

| Field | Type | Length | Format | Example |
|-------|------|--------|--------|---------|
| `service_name` | String | 1–64 chars | Alphanumeric + `-` | `api-backend`, `db-worker` |
| `instance_id` | String | 1–64 chars | Alphanumeric + `-` | `i-0a1b2c3d` (AWS), `pod-xyz789` (k8s) |
| `node_id` | UUID | 36 chars | RFC 4122 format | `a0000000-0000-0000-0000-000000000001` |

### 4.2 Uniqueness

- `node_id` is globally unique across all instances and time (generated by SmartLoad at registration)
- `service_name` + `instance_id` should also be unique within a deployment (operator-provided)
- Together, all three form a fully traceable identity: `api-backend/i-0a1b2c3d/a0000000-0000-0000-0000-000000000001`

### 4.3 Node Registration

When a backend node registers with SmartLoad:

1. **Operator provides:** `service_name`, `instance_id`, `host`, `port`, `weight`
2. **SmartLoad generates:** `node_id` (UUID)
3. **All telemetry from that node** includes all three identifiers

No telemetry is accepted without a valid `node_id` in the `backend_nodes` reference table.

## 5. Telemetry Record Format (JSON)

### 5.1 Simplified JSON Structure

A single telemetry record emitted by a backend node via OTLP or HTTP push:

```json
{
  "timestamp": "2026-03-28T14:23:45.123Z",
  "service_name": "api-backend",
  "instance_id": "i-0a1b2c3d",
  "node_id": "a0000000-0000-0000-0000-000000000001",
  
  "metrics": {
    "smartload.request.latency_ms": 87.5,
    "smartload.request.count": 42,
    "smartload.error.rate": 0.024,
    "smartload.backend.cpu_usage": 0.52,
    "smartload.backend.memory_usage": 0.68,
    "smartload.routing.decision_engine": "rl_driven"
  },
  
  "attributes": {
    "source": "real",
    "environment": "production",
    "region": "us-east-1"
  }
}
```

### 5.2 Detailed Field Specification

#### Top-level fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `timestamp` | ISO 8601 string | Yes | Time the metrics were collected (UTC, millisecond precision) |
| `service_name` | String | Yes | Name of the service emitting telemetry |
| `instance_id` | String | Yes | Cloud/orchestrator instance identifier |
| `node_id` | UUID string | Yes | SmartLoad-assigned unique node identifier |
| `metrics` | Object | Yes | Key-value pairs of metric names → values |
| `attributes` | Object | No | Optional tags for filtering, grouping (source, env, region, etc.) |

#### Metrics object

The `metrics` object is a flat key-value map where keys are metric names (following section 2 naming rules) and values are numeric (float or int).

**Never nest metrics:** ❌ Bad: `{"request": {"latency": 87}}` → ✅ Good: `{"smartload.request.latency_ms": 87}`

#### Attributes object (optional)

Common attributes for filtering:

| Attribute | Type | Values | Notes |
|-----------|------|--------|-------|
| `source` | String | `real`, `synthetic`, `borg`, `alibaba`, `azure`, `planetlab`, `bitbrains`, `nab`, `yahoo_smd` | Data origin; required for ML filtering |
| `environment` | String | `development`, `staging`, `production` | Deployment environment |
| `region` | String | AWS region codes, datacenter names, etc. | Geographic location hint |
| `availability_zone` | String | `us-east-1a`, etc. | Finer-grained location |

## 6. Metric Specifications

### 6.1 Required Metrics

These metrics **MUST** be present in every telemetry record. Records missing any of these are rejected by the collector.

#### `smartload.request.latency_ms`

| Property | Value |
|----------|-------|
| **Type** | Float |
| **Unit** | Milliseconds |
| **Range** | 0 – 10000 |
| **Description** | Time elapsed from request receipt to response completion on the backend node |
| **Aggregation** | Average over collection interval (typically 1 minute) |
| **Example** | `87.5` |

**Validation rules:**
- Must be >= 0
- If > 10000 ms, log warning but accept (may indicate degradation)
- Null/missing → record rejected

---

#### `smartload.request.count`

| Property | Value |
|----------|-------|
| **Type** | Integer |
| **Unit** | Count |
| **Range** | 0 – ∞ |
| **Description** | Number of requests handled by this node during the collection interval |
| **Aggregation** | Sum over collection interval |
| **Example** | `42` |

**Validation rules:**
- Must be >= 0
- Integer only (no decimals)
- Null/missing → record rejected

---

#### `smartload.error.rate`

| Property | Value |
|----------|-------|
| **Type** | Float |
| **Unit** | Ratio |
| **Range** | 0.0 – 1.0 |
| **Description** | Fraction of requests that returned a 5xx status code during the collection interval |
| **Aggregation** | Average over collection interval |
| **Example** | `0.024` (2.4% error rate) |

**Validation rules:**
- Must be in range [0.0, 1.0] (strict)
- If > 1.0, record rejected
- If < 0.0, record rejected
- Null/missing → record rejected

---

### 6.2 Optional Metrics

These metrics are **highly recommended** for autoscaling and anomaly detection but not strictly required. If absent, defaults apply.

#### `smartload.backend.cpu_usage`

| Property | Value |
|----------|-------|
| **Type** | Float |
| **Unit** | Ratio (percent normalized) |
| **Range** | 0.0 – 1.0 |
| **Description** | CPU utilization of the backend node as a fraction of available capacity |
| **Aggregation** | Average over collection interval |
| **Example** | `0.52` (52% CPU) |

**Validation rules:**
- Must be in range [0.0, 1.0]
- Null → impute with node's 7-day median CPU
- If missing, autoscaling decisions degrade to latency-only triggers

---

#### `smartload.backend.memory_usage`

| Property | Value |
|----------|-------|
| **Type** | Float |
| **Unit** | Ratio (percent normalized) |
| **Range** | 0.0 – 1.0 |
| **Description** | Memory utilization of the backend node as a fraction of available capacity |
| **Aggregation** | Average over collection interval |
| **Example** | `0.68` (68% memory) |

**Validation rules:**
- Must be in range [0.0, 1.0]
- Null → impute with node's 7-day median memory
- If missing, anomaly detection operates without memory signal

---

#### `smartload.routing.decision_engine`

| Property | Value |
|----------|-------|
| **Type** | String (enumeration) |
| **Values** | `round_robin`, `least_connections`, `weighted`, `rl_driven`, `forecast_driven` |
| **Description** | The routing engine used to select this node for the current request window |
| **Example** | `rl_driven` |

**Notes:**
- Informational only — used for auditing and dashboard filtering
- Null is acceptable — indicates no specific engine (default policy)

---

### 6.3 Metric Validation Matrix

| Metric | Required? | Type | Range | Null handling | SLA impact if missing |
|--------|-----------|------|-------|---|---|
| `smartload.request.latency_ms` | ✅ Yes | Float | [0, 10000] | Reject row | High — routing signal lost |
| `smartload.request.count` | ✅ Yes | Int | [0, ∞) | Reject row | High — load signal lost |
| `smartload.error.rate` | ✅ Yes | Float | [0.0, 1.0] | Reject row | High — anomaly detection fails |
| `smartload.backend.cpu_usage` | ❌ Optional | Float | [0.0, 1.0] | Impute median | Medium — autoscaling less aggressive |
| `smartload.backend.memory_usage` | ❌ Optional | Float | [0.0, 1.0] | Impute median | Low — redundant with CPU |
| `smartload.routing.decision_engine` | ❌ Optional | String | ENUM | Accept null | None — informational only |

## 7. Data Aggregation & Granularity

### 7.1 Three-Tier Aggregation

SmartLoad stores telemetry at three granularities:

| Tier | Interval | Table | Retention | Use case |
|------|----------|-------|-----------|----------|
| **Raw** | Real-time (sub-minute) | `telemetry_metrics` (raw) | 7 days | Debugging, incident response, fine-grained anomaly detection |
| **1-minute** | 1 minute | `telemetry_1min` (continuous aggregate) | 30 days | Dashboard, alerting, forecasting training |
| **1-hour** | 1 hour | `telemetry_hourly` (continuous aggregate) | 60+ days | Long-term trends, ML baseline training, compliance reporting |

### 7.2 Aggregation Logic

**Raw → 1-min:**

```sql
SELECT
  node_id,
  time_bucket('1 minute', time) AS bucket,
  AVG(latency_ms) AS smartload.request.latency_ms,
  SUM(request_count) AS smartload.request.count,
  AVG(error_rate) AS smartload.error.rate,
  AVG(cpu_usage) AS smartload.backend.cpu_usage,
  AVG(memory_usage) AS smartload.backend.memory_usage
FROM telemetry_metrics
GROUP BY node_id, bucket
```

**1-min → 1-hour:**

```sql
SELECT
  node_id,
  time_bucket('1 hour', time) AS bucket,
  AVG(smartload.request.latency_ms) AS smartload.request.latency_ms,
  SUM(smartload.request.count) AS smartload.request.count,
  AVG(smartload.error.rate) AS smartload.error.rate,
  AVG(smartload.backend.cpu_usage) AS smartload.backend.cpu_usage,
  AVG(smartload.backend.memory_usage) AS smartload.backend.memory_usage
FROM telemetry_1min
GROUP BY node_id, bucket
```

### 7.3 Gap Handling

If a backend node does not emit telemetry for >5 consecutive minutes:

- **Action:** Forward-fill the last known value for up to 5 minutes
- **After 5 minutes:** Mark node as unhealthy (3 consecutive health-check failures)
- **Resume:** Once data arrives again, resume normal aggregation (no backfill of missing intervals)

## 8. Data Source Tagging

### 8.1 Source Enum

Every telemetry record includes a `source` attribute indicating its origin:

| Source | Meaning | ML use | Notes |
|--------|---------|--------|-------|
| `real` | Data from actual production backend nodes | Training on production patterns | Primary signal; highest priority |
| `synthetic` | Artificially generated or injected data | Anomaly label injection, load testing | Clearly marked; separable from real |
| `borg` | Google Cluster Data traces (Borg) | RL training, forecasting baseline | Public dataset; labeled with timestamps |
| `alibaba` | Alibaba microservice traces | Forecasting training, RL simulation | Downsampled to per-node metrics |
| `azure` | Azure VM metrics dataset | Forecasting training, autoscaling validation | 5-minute granularity; resampled to 1-min |
| `planetlab` | PlanetLab CPU utilization traces | Forecasting training (CPU only) | Historical archive; no latency data |
| `bitbrains` | BitBrains workload traces | Forecasting training, autoscaling baseline | Realistic VM workloads; high quality |
| `nab` | Numenta Anomaly Benchmark | Anomaly detection training | Pre-labeled anomalies; univariate |
| `yahoo_smd` | Yahoo Server Metrics Dataset | Anomaly detection training, baseline | Pre-labeled anomalies; multivariate |

### 8.2 Source Filtering

All ML modules **must filter by source** during training and inference:

```python
# Example: Forecasting training only on real + blue-chip datasets
training_data = telemetry[
    telemetry['source'].isin(['real', 'azure', 'bitbrains'])
]
```

Mixing sources without deliberate validation is prohibited — data distributions differ significantly.

### 8.3 Synthetic Injection Guidelines

When injecting synthetic data (e.g., for anomaly labeling):

1. **Always tag with `source='synthetic'`**
2. **Document the injection method** (e.g., "CPU spike to 0.95 for 5 minutes")
3. **Keep synthetic separate** from real data during visualization
4. **Log to audit table** whenever synthetic data is introduced

## 9. Acceptance Criteria Checklist

Before deployment, verify:

- [ ] All required metrics are present in sample records
- [ ] Timestamp format is ISO 8601 UTC with millisecond precision
- [ ] Server identifiers (service_name, instance_id, node_id) are populated
- [ ] Metric names follow `smartload.<domain>.<metric>` convention
- [ ] Metric values are within specified ranges or properly rejected
- [ ] 1-minute and 1-hour aggregates are computed correctly
- [ ] Data source is tagged (no null `source` values)
- [ ] Null handling follows specification (reject vs impute vs accept)
- [ ] Example JSON record matches schema
- [ ] Telemetry collector configuration references this document
- [ ] Dashboard queries reference this schema for metric names
- [ ] ML pipeline validation rules enforce metric constraints

### 10.3 Invalid Record Examples

**❌ Missing required metric:**
```json
{
  "timestamp": "2026-03-28T14:23:45.123Z",
  "service_name": "api-backend",
  "instance_id": "i-0a1b2c3d",
  "node_id": "a0000000-0000-0000-0000-000000000001",
  "metrics": {
    "smartload.request.latency_ms": 87.5,
    "smartload.request.count": 42
    // ERROR: smartload.error.rate is missing
  }
}
```

**❌ Out-of-range error rate:**
```json
{
  "metrics": {
    "smartload.error.rate": 1.5  // ERROR: must be [0.0, 1.0]
  }
}
```

**❌ Timestamp not in UTC:**
```json
{
  "timestamp": "2026-03-28T14:23:45.123+02:00"  // ERROR: must end with Z
}
```

**❌ Nested metrics (violates flat structure):**
```json
{
  "metrics": {
    "smartload": {
      "request": {
        "latency_ms": 87.5  // ERROR: must be flat keys
      }
    }
  }
}
```

## 11. Collector Configuration Reference

Backend nodes emit telemetry via OTLP/gRPC or HTTP. The SmartLoad collector is configured to ingest records matching this schema. See `/docs/collector-config.yaml` for collector setup.

**OTLP Endpoint:** `http://<collector-host>:4317` (gRPC) or `http://<collector-host>:4318` (HTTP)

## 12. Frozen Schema Commitments

By freezing this schema, SmartLoad commits to:

1. **No breaking changes** in v1 — all fields remain stable
2. **Backward compatibility** — new optional metrics may be added only by minor version bump (v1.1, v1.2)
3. **Forward compatibility** — clients must ignore unknown fields gracefully
4. **Graceful deprecation** — if a metric must be removed, a 6-month notice period applies

Any non-backward-compatible change requires:
- Public notice (30 days minimum)
- Coordinated migration (collectors updated before DB changes)
- Major version bump (v2.0)
