The two cleverest queries

-- RL_STATE_QUERY: SQL pivots three metric_name rows into three columns
SELECT
    instance,
    AVG(CASE WHEN metric_name = 'request_latency_ms' THEN value END) AS latency,
    SUM(CASE WHEN metric_name = 'request_count'      THEN value END) AS request_count,
    MAX(CASE WHEN metric_name = 'error_rate'         THEN value END) AS error_rate
FROM metrics
WHERE time > NOW() - %s::interval
GROUP BY instance
ORDER BY instance;

-- BACKEND_HEALTH_QUERY: most-recent-per-group via DISTINCT ON
SELECT DISTINCT ON (backend_id)
    backend_id, status, score, time
FROM backend_health
WHERE time > NOW() - %s::interval
ORDER BY backend_id, time DESC;

Why two log sinks? The first goes to docker logs. The second is tailed by lb-otel-shipper. Path is /nginx-logs/access.log — NOT /var/log/nginx/access.log — because the Alpine base symlinks access.log → /dev/stdout, which can't be tailed.
Why a static 5-backend block? Open-source NGINX doesn't round-robin across DNS A-records, and lacks the Plus-only resolve directive. The autoscaler toggles running state of these 5 fixed containers — never creates/destroys — keeping NGINX's static block valid. proxy_next_upstream retries past stopped members.

3.2 · lb-otel-shipper — log tail → OTLP

Python T1.2

A 260-line sidecar that tails NGINX's JSON access log and emits one OTLP/HTTP-JSON gauge data point per request, per metric.

Why "Approach B" (log shipper) instead of NGINX-OTel module? The module aggregates upstream of the DB. SmartLoad's anomaly + RL queries compute STDDEV/MAX over rolling windows — that requires per-request rows, not pre-aggregated histograms. The shipper preserves fidelity.

The OTLP envelope construction

def build_envelope(datapoints):
    by_name = {}
    for name, value, ts_ns, backend in datapoints:
        by_name.setdefault(name, []).append({
            "timeUnixNano": str(ts_ns),
            "asDouble":     value,
            "attributes":   [
                {"key": "instance", "value": {"stringValue": backend}},
            ],
        })
    return {
        "resourceMetrics": [{
            "resource": {"attributes": [
                {"key": "service.name",        "value": {"stringValue": SERVICE_NAME}},
                {"key": "service.instance.id", "value": {"stringValue": INSTANCE_ID}},
            ]},
            "scopeMetrics": [{"metrics": [
                {"name": name, "gauge": {"dataPoints": dps}}
                for name, dps in by_name.items()
            ]}],
        }],
    }
The instance-attribute trick Resource attributes (service.name, service.instance.id) identify the shipper. The per-datapoint instance attribute identifies the backend that handled the request. The telemetry parser prefers the per-datapoint one — so metrics.instance stores the backend, not the shipper.

Fire-and-forget POST + counters

def post_envelope(envelope):
    try:
        resp = requests.post(COLLECTOR_URL, json=envelope, timeout=POST_TIMEOUT_S)
        if resp.status_code >= 400:
            _bump("batches_dropped");  return
        _bump("batches_sent")
    except requests.RequestException as exc:
        _bump("batches_dropped")
        log.warning("collector POST failed: %s", exc)

Backpressure must never reach the data plane. Any failure → count + log + drop. Heartbeat thread logs {lines_parsed, lines_skipped, batches_sent, batches_dropped} every 30 s.

Run-loop cycle (per service, identical shape)

Once bootstrapped, each AI service runs a single thread that interleaves Redis pub/sub message handling and tick-based inference. The pubsub get_message uses a 1-second timeout so policy updates land within one second; between messages, the loop runs an inference cycle every POLL_INTERVAL_SECONDS. Engine reconstruction on policy change keeps trained-model loading cheap (cached artifact) while honouring policy-derived constructor kwargs.

4.1 · anomaly-detector

Python Phase-1 wired (flag off)

Run-loop wiring (#138 round 1)

app.py is no longer a Phase-0 stub. When ANOMALY_RUNLOOP_ENABLED=true, the service runs a threaded loop that:

  1. resolves the engine via engine_base.select_engine(ANOMALY_ENGINE) with automatic fallback to threshold if the requested engine fails to load;
  2. polls ANOMALY_QUERY against TimescaleDB every POLL_INTERVAL_SECONDS (default 10 s) over a ANOMALY_WINDOW_SECONDS lookback;
  3. pivots the rows into one BackendFeatures per backend via runloop.build_features_from_rows;
  4. calls engine.score(features) for each backend;
  5. publishes AnomalyEvent envelopes to smartload.anomaly through the canonical publish_envelope helper, filtered by a publish gate that respects safe_mode and anomaly_response (auto-isolate vs advisory);
  6. subscribes to smartload.policy and rebuilds the engine on each update so policy-derived parameters (currently anomaly_latency_multiplier) take effect within one cycle. Stale publishes (lower policy_version) are dropped.

The pure-Python pieces live in services/anomaly-detector/runloop.py (engine bootstrap with fallback, policy payload parsing, row pivot, publish gate, payload shape) so they can be unit-tested without docker / Redis / DB. 18 unit tests at tests/unit/anomaly-detector/test_runloop.py.

The Phase-0 stub is preserved as the default: ANOMALY_RUNLOOP_ENABLED defaults to false per #138's one-service-at-a-time safety strategy. /health adds three engine fields when the loop is enabled: engine_type, engine_ready, last_inference_age_seconds.

Model handoff

The decision-plane integration boundary is now codified: a model author delivers (a) a trained artifact at services/anomaly-detector/models/<name>.pkl, and (b) an engines/<name>/engine.py exporting class <Name>Engine(AnomalyEngine) implementing score(features) -> AnomalyScore. The factory in engine_base.py dispatches by name. The run loop, Redis publishing, policy subscription, and fallback-to-baseline are owned by the integration layer — the model author never touches app.py.

    def __init__(self, latency_multiplier=3.0, error_rate_threshold=0.05, min_sample_count=10):
        self.latency_multiplier = latency_multiplier
        self.error_rate_threshold = error_rate_threshold
        self.min_sample_count = min_sample_count

    def score(self, features):
        if features.sample_count < self.min_sample_count:
            return AnomalyScore(features.backend_id, "healthy", 0.0)
        if features.error_rate > self.error_rate_threshold:
            return AnomalyScore(features.backend_id, "unhealthy",
                                min(1.0, features.error_rate / self.error_rate_threshold))
        if features.latency_rolling_mean_ms <= 0:
            return AnomalyScore(features.backend_id, "healthy", 0.0)
        ratio = features.latency_ms / features.latency_rolling_mean_ms
        if ratio > self.latency_multiplier:
            return AnomalyScore(features.backend_id, "degraded",
                                min(1.0, ratio / (self.latency_multiplier * 2)))
        return AnomalyScore(features.backend_id, "healthy", 0.0)

Moving-average baseline

class MovingAverageEngine(ForecastEngine):
    def __init__(self, horizon_minutes=5, window_samples=60):
        self.horizon_minutes = horizon_minutes
        self.window_samples = window_samples

    def forecast(self, history):
        rates = history.request_rates[-self.window_samples:]
        if not rates:
            return Forecast(self.horizon_minutes, 0.0, 0.0, 0.0)
        mean = sum(rates) / len(rates)
        if len(rates) >= 2:
            var = sum((r - mean) ** 2 for r in rates) / (len(rates) - 1)
            std = var ** 0.5
        else:
            std = 0.0
        return Forecast(
            horizon_minutes=self.horizon_minutes,
            predicted_rps=mean,
            confidence_lower=max(0.0, mean - std),
            confidence_upper=mean + std,
        )
Why sample variance (n−1)? The denominator (len(rates) - 1) gives the sample variance. The confidence band reflects uncertainty about the true mean rather than the observed one. max(0.0, mean - std) clamps the lower bound — RPS can't be negative.

app.py is no longer a Phase-0 stub. When RL_RUNLOOP_ENABLED=true, the service runs the same shape as anomaly-detector and forecasting, with three RL-specific extensions:

  1. resolves the policy via policy_base.select_policy(RL_POLICY) with automatic fallback to random_shadow if the requested policy fails to load.   2. polls RL_STATE_QUERY against TimescaleDB every POLL_INTERVAL_SECONDS (default 5 s) over a RL_WINDOW_SECONDS lookback;
  3. builds list[BackendState] via runloop.build_state_from_rows, classifying health locally with the same thresholds the threshold engine uses (latency > 200 ms → degraded; error_rate > 0.05 → unhealthy).   4. calls policy.act(state) to get a RoutingAction(mode, rankings);
  5. composes the published mode field via runloop.effective_mode() from three independent gates — see the diagram below;
  6. publishes a RoutingRecommendation envelope to smartload.routing with the policy-version join key;
  7. subscribes to smartload.policy and rebuilds the policy on each update so rl_exploration_rate / rl_confidence_threshold take effect within one cycle (kwargs are ignored gracefully by baselines that don't accept them).

def scale_out(self):
    for container in self._backends():           # sorted by replica number
        if container.status != "running":
            container.start()
            return container.name
    return None                                   # no stopped containers

def scale_in(self):
    running = [c for c in self._backends() if c.status == "running"]
    if not running: return None
    target = running[-1]                          # highest-numbered
    target.stop(timeout=5)
    return target.name

def _handle_policy_message(raw):

async function _fetchJson<T>(input: string, init?: RequestInit): Promise<T> {
  const r = await fetch(input, {
    ...init,
    headers: { "Content-Type": "application/json", ...(init?.headers || {}) },
  });
  const text = await r.text();
  let body: any = {};
  try { body = text ? JSON.parse(text) : {}; }
  catch { body = { error: text }; }
  if (!r.ok) {
    const err = new Error(body?.error || `HTTP ${r.status}`);
    (err as any).status = r.status;
    (err as any).field  = body?.field;     // round-trips server-side validation hint
    throw err;
  }
  return body as T;
}

    service, instance, metric_name,
    AVG(value), MAX(value), MIN(value), SUM(value), STDDEV(value), COUNT(*)
FROM metrics
GROUP BY bucket, service, instance, metric_name
WITH NO DATA;

SELECT add_continuous_aggregate_policy('metrics_1min',
    start_offset      => INTERVAL '1 hour',
    end_offset        => INTERVAL '2 minutes',
    schedule_interval => INTERVAL '1 minute');
P95 is NOT computed here PERCENTILE_CONT is an ordered-set aggregate and is rejected by TimescaleDB CAGGs (the materialized view would fail to create). Dashboards compute P95 on raw metrics over a bounded window — cheap at SmartLoad scale.

Datasource provisioning trick

deleteDatasources:
  - { name: Prometheus,  orgId: 1 }
  - { name: TimescaleDB, orgId: 1 }

datasources:
  - name: Prometheus
    uid: prometheus            # pinned UID — dashboard JSON references this
    type: prometheus
    url: http://prometheus:9090
    isDefault: true
  - name: TimescaleDB
    uid: timescaledb
    type: postgres
    url: timescaledb:5432
    secureJsonData:
      password: "${TIMESCALEDB_PASSWORD}"

deleteDatasources runs before provisioning — required because pinned UIDs collide with prior auto-generated UIDs across restarts. Without it, startup fails with "data source not found".
