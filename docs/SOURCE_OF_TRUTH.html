2. Executive Overview

What SmartLoad is

SmartLoad is a microservice-based middleware platform that acts simultaneously as (a) an adaptive load balancer, (b) a proactive autoscaler, and (c) a failure-aware controller. It receives all client HTTP traffic, decides in real time which backend service should handle each request, and dynamically scales the backend pool ahead of demand.

Why it exists

Traditional load balancers (NGINX, HAProxy) use fixed routing rules that do not adapt to workload changes. Cloud autoscalers (AWS, Azure, GCP) react only after load increases, causing latency spikes. Kubernetes brings flexibility but adds operational complexity that prices out small/medium organizations. Organizations end up assembling several independent tools — load balancers, autoscalers, monitoring, anomaly alerting — without any unified decision-making intelligence.

Problem statement

Modern digital platforms face unpredictable workload patterns that overwhelm fixed-capacity systems. There is no lightweight, intelligent middleware that integrates classical routing, RL-based adaptive routing, time-series forecasting, anomaly detection, and proactive autoscaling into a single coherent decision loop with deterministic safety fallbacks.

Key innovation

The Decision Layer is a multi-engine controller (not an algorithm selector). All decision engines run in parallel on the same telemetry, publish to a shared Redis control bus, and the load balancer applies a strict routing decision hierarchy: anomaly constraints first → RL recommendations second → classical fallback third. This ensemble approach delivers adaptiveness and robustness.

Intended outcomes

  • Research contribution: a publishable comparative study of classical vs AI-driven workload distribution on standard cluster traces.
  • Product angle: a lightweight middleware (or future SaaS) for small/medium teams who need adaptive load management without Kubernetes overhead.
Headline target metrics: P95 latency < 200 ms (nominal) / < 300 ms (high load) · Forecasting MAPE < 20% · Anomaly F1 > 0.80 · Anomaly reroute ≤ 2 monitoring intervals · Scale reaction < 2 min · SmartLoad CPU overhead < 10%.

4. System Design Principles

Canonical Design Intent

SmartLoad is middleware, not a monolith. Every later section, deep dive, and review checklist must obey the principles in this section. When a current implementation conflicts with these principles, that conflict is a gap to close — not a license to ignore the principle. These principles are the constitution. The rest of the document is the law.

The principles below are non-negotiable for the canonical design. They do not all have to be implemented today, but no implementation choice may silently violate them. If a tradeoff requires bending a principle, the tension must be recorded explicitly under the relevant module's Gap to Close or Design Tension block.

1

Middleware-first design

SmartLoad's value is being a thin, replaceable, observable intermediary — not a feature-rich application platform.

Impact: No business logic in the routing path. No long-running per-request computation in the load balancer. No persistent client state. Every internal service is replaceable behind its contract.

2

Control plane vs data plane separation

Decisions about routing must not block routing itself. Intelligence runs off the request path; the request path only consumes pre-computed signals.

Impact: NGINX never queries TimescaleDB or Redis on the request path. AI services never proxy requests. The data plane reads only its in-memory effective config; the control plane updates that config asynchronously.

3

Explicit, versionable contracts

Every cross-service interaction must be a typed, documented contract — Redis message schema, REST endpoint, or SQL query constant.

Impact: No ad-hoc JSON. services/shared/contracts.py is canonical for messages; services/shared/queries.py is canonical for SQL. Breaking changes require a new version, not in-place edits.

4

Graceful degradation by default

Loss of any AI service must reduce SmartLoad to classical routing, never to outage.

Impact: Every consumer of an AI signal has a fallback path. NGINX uses last-known-good config when Redis dies. Anomaly detector falls back from Isolation Forest to threshold rule. Forecaster falls back from ARIMA to moving average. Operator safe_mode short-circuits all AI in one flag.

5

Observability is a first-class output

A middleware that cannot be debugged in production is a liability. Telemetry is a feature, not an afterthought.

Impact: Every service emits structured logs, OTel metrics, and a /health endpoint. Every routing decision is attributable. Every Redis publish is loggable with envelope metadata. Grafana dashboards are part of the deliverable, not optional.

6

Replaceable decision engines

Anomaly, forecasting, and RL are research artifacts under active iteration. They must be swappable without touching the LB or the autoscaler.

Impact: Engines own only their algorithm + their publish channel. The LB sidecar and autoscaler depend on the message contract, not the engine implementation. Swapping Isolation Forest → LSTM autoencoder is a change inside one service and one model file.

7

Stateless on the request path

Horizontal scaling of NGINX requires that no request carry hidden state through the load balancer.

Impact: No session affinity. No per-client memory. The LB carries only its current effective routing config (a small, regenerable structure), nothing per-request beyond the in-flight buffer.

8

Single source of record per data class

Every kind of data has exactly one authoritative writer. Multiple writers to the same data is the most common cause of architectural decay in middleware.

Impact: TimescaleDB owns telemetry rows (Telemetry Service is the only writer). Redis owns ephemeral signals. Policy Manager owns policy state. AI engines own their decision channels but never each other's.

9

Routing hierarchy is law

Anomaly constraints > policy > RL recommendation > classical fallback. This order is not negotiable; it is the safety contract that lets RL be trusted at all.

Impact: The LB sidecar enforces the order, not any individual engine. RL never sees an UNHEALTHY backend in its action space. Policy safe_mode can short-circuit RL but never bypasses anomaly exclusion.

10

Prototype realism with production ambition

SmartLoad is a graduation project, but its design must be defensible as a real middleware. Not every feature ships, but every shipped feature must be production-shaped.

Impact: docker-compose is acceptable for the prototype; the design must remain trivially portable to Kubernetes. Redis is in-memory for the prototype; the contract assumes message loss is possible. Every "we'll add this later" must be marked as a gap, not silently scoped out.

11

Low coupling between routing and intelligence

The LB must function with zero AI services running. AI services must function without each other.

Impact: No service imports another service's code. Services only see shared/contracts.py + shared/queries.py. A failed RL engine does not stop the anomaly detector. A failed anomaly detector does not stop the forecaster.

12

Scalable service boundaries

Every internal service must be horizontally replicable, even if only one replica runs in the prototype.

Impact: No service caches authoritative state in process memory without a TTL or refresh path. Redis pub/sub fan-out tolerates multiple subscribers. Telemetry writes are idempotent. Policy is pull-on-startup + push-on-change.

How these principles are applied later in this document

  • Every Design Contract in §8 is judged against principles 1, 3, 6, 8, 11.
  • Every Review Checklist derives its items from the principles relevant to the area being reviewed.
  • Every Gap to Close notes which principle the gap currently violates or under-realizes.
  • The Routing & Decision Authority section (§12) is the operational embodiment of principles 2, 4, 9.
  • The Control Plane vs Data Plane section (§13) is the operational embodiment of principles 2, 7.

5. Big Picture Architecture

Architecture summary

SmartLoad is organized as a cloud-native microservice system with four logical layers communicating over a closed feedback loop. Each layer can evolve independently provided it respects the published contracts (Redis message schemas in services/shared/contracts.py and SQL queries in services/shared/queries.py).

The four canonical layers

  1. Ingress & Traffic Routing — accepts client HTTP, applies effective routing decisions to backend pool. Components: API gateway concept (logical), NGINX Load Balancer, sidecar Routing Controller (planned T2.1).
  2. Telemetry & Observability — collects, normalizes, stores all operational metrics. Components: OTel SDK in services, OTel Collector, Telemetry Service, TimescaleDB, Prometheus, Grafana.
  3. Decision Intelligence — multi-engine controller producing signals from telemetry. Components: Anomaly Detector, Forecasting Engine, RL Engine, Classical LB Engine (logical, embedded in the LB).
  4. Control & Actuation — applies decisions to runtime. Components: Redis Pub/Sub control bus, NGINX routing controller, Autoscaler, Policy Manager.

System context

Layered architecture

Closed-loop control (MAPE cycle)

SmartLoad operates as a continuous closed-loop controller:

  1. Monitor — telemetry collected from NGINX + backends.
  2. Analyze — decision engines (anomaly, forecast, RL) run on the metrics.
  3. Plan — signals published to Redis; routing controller and autoscaler merge them under policy.
  4. Execute — NGINX upstream weights changed; backend instances added/removed via Docker SDK.
  5. New telemetry reflects the post-action state, closing the loop.

Main runtime flow (request path)

  1. Client sends HTTP request → NGINX Load Balancer (internal port 80, exposed externally as 8080 via docker-compose).
  2. NGINX picks backend per current effective config (anomaly-filtered + RL-weighted or classical).
  3. Backend processes; latency / status logged.
  4. NGINX writes a JSON access log line per request to a shared volume; the lb-otel-shipper sidecar tails the log, parses each line, and POSTs OTLP/HTTP-JSON (one gauge data point per request, fire-and-forget) → OTel Collector → TimescaleDB via Telemetry Service (port 8081).
  5. Decision engines query TimescaleDB on cycle:
    • Anomaly Detector (5s) → publishes AnomalyEvent to smartload.anomaly.
    • Forecasting (60s) → publishes ForecastResult to smartload.forecast.
    • RL Engine (5s) → publishes RoutingRecommendation to smartload.routing.
  6. LB sidecar (Phase 2 / T2.1) consumes smartload.anomaly + smartload.routing + smartload.policy → updates NGINX upstream weights; Autoscaler consumes smartload.forecast → starts/stops backend containers; Policy Manager publishes smartload.policy on change.
  7. Cycle repeats.

6. Canonical Runtime Model

Canonical Design Intent

This section answers a single architectural question: what runs on the request path, and what runs off it? The request path must remain lightweight, deterministic, and free of AI dependencies. All decision intelligence runs on a separate cycle and only mutates the data plane through pre-computed, asynchronous signals. This split is what makes the system safe to extend.

Two execution surfaces

SmartLoad has exactly two execution surfaces. Every component must belong to exactly one. A component that straddles both surfaces is a design tension and must be split.

SurfaceWhat it isLatency budgetAllowed dependenciesForbidden behavior
Data plane Hot path The request-handling path: client → NGINX → backend → client. Per-request overhead < 5 ms P99 at ≤ 1000 rps. Local NGINX config only. Optional in-process sidecar with last-known-good config in memory. Network calls to Redis or TimescaleDB. Calls to AI services. Synchronous waits on policy.
Control plane Cold path Telemetry collection, decision engines, autoscaling, policy distribution. Cycles measured in seconds (5 s, 60 s) — no per-request budget. TimescaleDB reads, Redis pub/sub, Docker SDK, REST APIs between services. Anything that blocks the data plane. Synchronous fan-out that requires all subscribers to ack.

What runs on the request path

  • NGINX — accepts requests, applies its currently loaded upstream block (round-robin / least-conn / weighted), forwards. Writes a JSON access log line per request (to stdout for docker compose logs + to a shared volume for the shipper).
  • Backend health checks — passive (NGINX max_fails/fail_timeout) and a planned active probe; both run as part of the LB process, not as a separate service.
  • NGINX access log write — buffered, fire-and-forget. The request never blocks on log emission. Per-request OTel data points are produced off the request path by the lb-otel-shipper sidecar reading that log.

What runs off the request path

  • lb-otel-shipper — sidecar to NGINX. Tails the JSON access log (shared volume), parses each line, emits one OTLP/HTTP-JSON gauge data point per metric (request_count, request_latency_ms, error_rate) to the OTel Collector. Drops on collector outage; never feeds back to NGINX.
  • OTel Collector — pulls/receives metrics, forwards to Telemetry Service.
  • Telemetry Service — writes rows into TimescaleDB.
  • Anomaly Detector — 5 s cycle. Reads TimescaleDB, publishes to smartload.anomaly.
  • Forecasting Engine — 60 s cycle. Reads TimescaleDB, publishes to smartload.forecast.
  • RL Engine — 5 s cycle. Reads TimescaleDB + anomaly flags, publishes to smartload.routing.
  • Autoscaler — event-driven on smartload.forecast. Calls Docker SDK.
  • Policy Manager — event-driven on REST POST /policy. Publishes to smartload.policy.
  • LB Sidecar T2.1 target — subscribes to anomaly + routing + policy channels, regenerates nginx.conf, runs nginx -s reload. This is the only control-plane process that touches data-plane configuration.

Synchronicity rules

InteractionRuleWhy
Service → TimescaleDB (read)Synchronous, off the request path.Decision engines need consistent metric snapshots.
Telemetry Service → TimescaleDB (write)Asynchronous batched writes preferred; synchronous acceptable in the prototype.Don't lose telemetry to backpressure.
Engine → Redis (publish)Asynchronous, fire-and-forget.Subscriber failure must not stop the publisher.
LB Sidecar → NGINX (reload)Asynchronous; sidecar regenerates config and signals a graceful reload.NGINX continues serving in-flight requests on old config.
Policy Manager → all subscribersPush (Redis publish) plus pull-on-startup via REST.New subscribers must converge without waiting for the next publish.
Operator → Policy ManagerSynchronous REST.Operator must see immediate confirmation that policy changed.

What must remain lightweight

  • The LB process — no embedded ML, no in-process Python, no heavy plugins.
  • The LB sidecar — pure subscriber + config-renderer. No business logic.
  • The shared client libraries (contracts.py, queries.py) — pure data classes and SQL strings, no behavior.

What may be heavy (and where)

  • RL training — runs offline, not in the live RL Engine container. The live container only loads policy.zip and runs inference.
  • Forecasting model fit — runs offline (or on a long cron). The live container only runs forecast(now).
  • Anomaly model fit — same. Heavy training, light inference.
  • EDA notebooks, dataset preprocessing — explicitly off-runtime. They produce artifacts (parquet files, pickled models) that the runtime services consume.
Anti-pattern: Embedding model training inside the live decision engine. This couples cycle latency to model size and turns model updates into deploys. The runtime must always load a pre-trained artifact from disk.

Review Checklist — Runtime Model

  • Does this component clearly belong to either the data plane or the control plane? Components that straddle both must be split.
  • Does any code on the request path make a network call to Redis, TimescaleDB, or another service? If yes, this is a violation of principle 2.
  • Does any control-plane component require a synchronous response from another control-plane component to complete its cycle? If yes, the dependency is a coupling risk.
  • Does the runtime container of any AI service contain training code, large datasets, or ML hyperparameter search? If yes, it should be moved to an offline pipeline.
  • Is every Redis publisher tolerant of zero subscribers? Every subscriber tolerant of stale or missing publishes?
  • Can the LB serve traffic correctly with all AI services stopped? (Must be yes.)

Canonical Design Intent

Every module below is described not just by what it does today, but by what it should own and never own — the structure that lets the module be reviewed, replaced, or scaled without rewriting the rest of SmartLoad. Each module has a Design Contract block stating its purpose, owned and forbidden responsibilities, inputs, outputs, contract surface, fallback behavior, scalability and observability expectations, plus current state, target state, and gap to close.

8.1 Load Balancer (NGINX) Canonical Wired

Purpose

The single entry point for all client HTTP traffic. Translates routing intelligence into concrete request-forwarding actions while preserving deterministic safety fallbacks.

Responsibilities

  • Accept HTTP/1.1 requests on port 80 (internal); exposed as 8080 on the host via docker-compose port mapping.
  • Apply current effective routing config (upstream weights and exclusions).
  • Run periodic health checks against backends and exclude unresponsive ones.
  • Write a structured JSON access log per request (timestamp, selected backend, latency, status) to stdout and to a shared volume — the volume is read by the lb-otel-shipper sidecar, which produces the actual OTLP emission off the request path.

Inputs

  • Client HTTP requests.
  • Routing config (statically generated initially; dynamically updated by sidecar in Phase 2).

Outputs

  • Forwarded requests to selected backend.
  • Per-request JSON access log to stdout (for docker compose logs) and to a shared volume /nginx-logs/access.log (for the shipper). Fields: timestamp, service, client_ip, request, status, backend, latency, upstream_latency.
  • Indirect (via lb-otel-shipper): canonical flat metric names — request_count, request_latency_ms, error_rate — emitted as one OTLP/HTTP-JSON gauge data point per request to the OTel Collector.

Dependencies

  • Shared volume nginx-logs mounted by NGINX (rw) and by the shipper (ro).
  • lb-otel-shipper sidecar — reads the access log and emits OTLP off the request path. Failure of the shipper does not affect request serving (NGINX keeps writing logs; metrics simply don't reach the DB until the shipper recovers).
  • Sidecar (Python or Go) for live config updates from Redis (planned T2.1) — separate from the shipper; this is the routing controller.

Internal logic

Phase 1: classical NGINX upstream block with all healthy backends in round-robin. Health checks remove failures within 2 cycles.

Phase 2 (T2.1): sidecar process subscribes to:

  • smartload.anomaly → maintain set of UNHEALTHY backend IDs and remove from upstream.
  • smartload.routing → if mode=active, set upstream weight=score proportional to RL scores.
  • smartload.policy → if safe_mode=true, reset all weights to equal and stop applying RL.
After applying changes, the sidecar regenerates nginx.conf and runs nginx -s reload (graceful reload).

Routing decision hierarchy (canonical)

  1. Anomaly constraints first: drop UNHEALTHY backends from the upstream list.
  2. Active policy: if safe_mode=true, switch to equal weights and stop reading RL.
  3. RL recommendation: when allowed and available, set weights from RoutingRecommendation.server_rankings.
  4. Classical fallback: round-robin / least-connections is always available if RL is missing, warming up, or stale.

State handled

  • NGINX upstream config (regenerated by sidecar).
  • Stateless w.r.t. individual requests — no session affinity.

Fallback behavior

If Redis is unreachable or the sidecar dies: NGINX continues serving traffic with the last successfully applied config. If anomaly signals are stale, NGINX still has health checks as a second-line defense.

Constraints

P99 routing-latency overhead < 5 ms at ≤ 1000 req/s with ≥ 1 healthy backend.

8.1.1 LB OTel Shipper Canonical Wired T1.2 wired

Purpose

A small Python sidecar to NGINX whose only job is converting NGINX's per-request JSON access log into OTLP/HTTP-JSON metric data points and POSTing them to the OTel Collector. Decouples NGINX (the data plane) from telemetry plumbing — NGINX writes a log line and never connects to the collector itself.

Why it exists (vs. an in-NGINX OTel module)

SmartLoad's AI engines query AVG(value), MAX(value), STDDEV(value) over rolling windows from the metrics table. To produce meaningful STDDEV/MAX the table must contain per-request samples. The candidate alternative — F5's nginx-otel module + collector spanmetrics connector — aggregates spans into windowed means before they ever leave the collector, flattening the per-request distribution. The shipper preserves per-request fidelity by emitting one OTLP gauge data point per HTTP request.

Responsibilities

  • Tail /nginx-logs/access.log (seek from end on start; do not re-emit historical lines).
  • Parse each JSON log line; tolerate malformed lines (log + skip, never crash).
  • For each parsed line, emit three OTLP gauge data points with shared resource attributes:
    • request_count = 1
    • request_latency_ms = latency field × 1000 (NGINX $request_time is seconds)
    • error_rate = 1 if status ≥ 500 else 0 (engines aggregate via AVG)
  • Set resource attributes service.name=load-balancer and instance=<hostname>.
  • POST OTLP/HTTP-JSON to http://otel-collector:4318/v1/metrics with a strict timeout. On any error (timeout, conn refused, 5xx), log + drop. Never raise into the tailing loop.

Inputs

  • Read-only mount of the nginx-logs shared volume at /nginx-logs/. (Not /var/log/nginx/ — the nginx:alpine base image symlinks access.log there to /dev/stdout, which is unseekable.)

Outputs

  • OTLP/HTTP-JSON metric batches to the OTel Collector (POST /v1/metrics).
  • Process logs to stdout (own observability — line counts, dropped-batch counts).

Dependencies

  • NGINX writing the access log to the shared volume.
  • OTel Collector reachable at otel-collector:4318. Down → metrics dropped silently for that interval; the request path is unaffected.

Internal logic

Single-process, single-thread tail loop with a small thread pool for outbound HTTP. The OTLP payload schema matches Telemetry Service (§8.3)'s accepted shape exactly: resourceMetrics[].scopeMetrics[].metrics[].gauge.dataPoints[] with asInt/asDouble values and nanosecond timeUnixNano. No histograms (telemetry drops histograms — rows_dropped_shape).

State handled

  • Last-read file position (in-process; restart loses position by design — start_at: end).
  • No persistence to disk or DB.

Fallback behavior

Three independent failure modes, all isolated from the request path:

  • Shipper down → NGINX keeps serving + writing logs; metrics simply don't reach the DB until the shipper restarts. Log file accumulates on the volume; bounded by NGINX's own log rotation.
  • Collector down → shipper logs the error, drops the batch, continues tailing. No retries (fire-and-forget).
  • Telemetry Service down (downstream of collector) → collector's otlphttp/telemetry exporter handles its own retry/backoff; shipper unaffected.

Constraints

  • Memory footprint < 50 MB.
  • Sustained throughput ≥ 1000 req/s without falling behind the log file (verified by integration test).
  • Zero impact on NGINX request latency under shipper failure.

8.2 Classical Routing Engine Canonical

Purpose

SmartLoad's deterministic safety net. Always-available routing logic that runs whenever AI signals are unavailable, stale, or disabled. Also serves as the comparison baseline for benchmarks.

Algorithms

  • Round-robin — default; fair cyclical distribution across all healthy backends.
  • Least-connections — routes to the backend currently handling fewest active requests.
  • Weighted round-robin — optional; respects backend weight in upstream config.

Why it matters

Reflects a core SmartLoad philosophy: intelligent components augment proven strategies, never replace them outright. Once shipped, the engine needs no maintenance.

Where it lives

Embedded inside the NGINX upstream configuration — no standalone microservice. The classical strategy is the result of how upstream weights are set when no RL signal applies.

Implementation readiness

DONE Round-robin works in the Phase 0 stack against the test-backend pool.

Owned responsibilities
Round-robin / least-connections / weighted-RR semantics — implemented natively by NGINX upstream config, not as a separate service.
Non-responsibilities
Must NOT be moved into a Python service. Must NOT depend on Redis or TimescaleDB. Must remain trivially deployable with no AI services running.

8.3 Telemetry Service Canonical Wired T1.1 wired

Purpose

The sensory system of SmartLoad. Receives OTLP metrics, writes them to TimescaleDB, exposes them as queryable JSON for AI services and operators.

Inputs / Outputs

  • In: OTLP metrics (port 4318 HTTP / 4317 gRPC) from OTel Collector.
  • Out: rows in metrics(time, service, instance, metric_name, value); HTTP GET /api/v1/metrics?service=&window=.

Internal logic

The OTel Collector forwards each metric batch to POST /v1/metrics via its otlphttp/telemetry exporter (encoding: json). The service walks the OTLP envelope, extracts gauge and sum data points into canonical (time, service, instance, metric_name, value) tuples, and persists them with psycopg2.extras.execute_batch(METRICS_INSERT, rows, page_size=500). Histogram / summary / exponentialHistogram are out of the SmartLoad metric set and are counted as rows_dropped_shape rather than persisted.

Backpressure containment: the ingress endpoint always returns 200 to the collector. DB-write failures bump rows_dropped_db and log; never silent and never propagated to the data plane.

Read API: GET /api/v1/metrics?service=&window= accepts Prometheus-style window strings (30s / 5m / 1h / 2d) and queries metrics with %s::interval, %s, %s bind params (SOT §11). Returns {service, window, rows: [...]}; row count capped at READ_API_ROW_LIMIT (default 10 000).

Observability: GET /api/v1/stats returns rows_written / batches_written / rows_dropped_db / rows_dropped_shape counters guarded by a threading.Lock.

8.11 Operator-Side Tools — Grafana + Operator UI Canonical Home + Policy + Audit + Actions shipped (slices #1, #2, #3)

Decision: Grafana for charts, lightweight Operator UI for transparency + override

The §5 context diagram has two arrows between the Operator and the SmartLoad middleware: policy / config updates (write) and alerts & dashboard (read). The read-side surface is rendered by two operator-side tools, both sitting outside the SmartLoad middleware bubble:

  • Grafana — time-series charts (Overview / Anomaly / Forecast / RL / Scaling). The thing operators look at to understand the data.
  • Operator UI — Flask BFF (port 8090) + React/Vite SPA, not Flask+Jinja+HTMX. The original "lightweight HTMX" plan was superseded in slice #1 (commit 6f89a13). The thing operators look at to understand the decisions and to act on them safely: live engine signals, policy editing with diff preview, audit log viewer, manual override actions with confirmation modals. Embeds Grafana iframes for charts (does not rebuild charting).

Neither tool is a SmartLoad layer. Neither owns a Redis channel, a TimescaleDB hypertable, or a decision path. Remove them tomorrow and every backend feature still works — operators just drop back to curl + docker logs + raw SQL.

Why two tools, not one

Grafana is excellent at charts and time-series correlation, weak at: confirming manual actions, project-specific decision explanation, in-place policy editing with validation feedback, audit log viewing in domain language. The Operator UI fills exactly those gaps. Building charts in the Operator UI would be duplicate work; running operator-grade governance flows through a Grafana annotation hack would be brittle.

Confirmation model (operator-grade safety)

Per locked design: the UI is not an approval gate for autonomous decisions. The autoscaler keeps reacting to forecasts, the anomaly detector keeps publishing, the LB keeps rerouting around unhealthy backends — none of these wait for an operator click. The UI is an approval gate only for operator-initiated manual overrides: manual scale, manual isolate, force route weights, and policy edits. Each of those gets a confirmation modal before the POST fires. This preserves system autonomy while ensuring no destructive operator click is one accidental keystroke away.

Source-of-record rules

  1. Telemetry is owned by Telemetry Service — no other service writes to metrics.
  2. Health is owned by Anomaly Detector — neither RL nor LB derives its own health view; both read through the anomaly channel.
  3. Routing weights are owned by the LB Sidecar — RL produces recommendations, not authoritative weights. The sidecar is the merge point.
  4. Scaling actions are owned by Autoscaler — only it calls Docker SDK; only it writes scaling_events.
  5. Policy is owned by Policy Manager — it is the only writer to config/policy.yaml and the only publisher to smartload.policy.

Dedup & ordering rules (canonical)

  • Dedup by event_id — every published message carries a UUID v4 (see §11). Subscribers that perform actions (e.g. Autoscaler, LB Sidecar reload) must dedup by event_id within a 5 min window so a re-publish never causes a double action.
  • Order by timestamp — pub/sub does not guarantee order across publishers, but each channel has exactly one publisher (rule above), so timestamp ordering is well-defined per channel.
  • Snapshot semantics for policy — every smartload.policy publish is a full snapshot, not a diff. A subscriber that joins late just consumes the next publish and is up to date. policy_version is a monotonic integer; subscribers that observe a gap (v3 then v5) know they missed v4 but their state is still consistent because they have the latest snapshot.

Anti-patterns to refuse

  • An AI service writing directly to metrics (forbidden — only Telemetry Service writes).
  • RL Engine deriving health flags by reading raw latency rather than subscribing to smartload.anomaly (duplicates ownership of "health"; risks divergence).
  • LB Sidecar reading TimescaleDB on the request path (violates principle 2; data plane must remain pure).
  • Policy Manager subscribing to its own smartload.policy channel for state (it owns the state; it should not depend on its own publish loop for correctness).
  • Two services writing to the same Redis channel (channels have one publisher; multiple subscribers are fine).

Review Checklist — Data Ownership

  • Does the new code introduce a second writer to any data class above? If yes, redesign.
  • Is every read either through the owner's contract (Redis channel, REST endpoint) or through the canonical store (read-only)?
  • Does any service derive a fact that another service is the source of record for? (E.g., health, routing weights, policy.) If yes, replace with subscription to the owner.
  • Are ephemeral signals (forecast, routing) treated as best-effort by their consumers? (Subscribers must tolerate gaps.)
  • Are persistent writes idempotent under retry?

10. Storage & Schema Authority

Canonical Design Intent

Storage is an architecture decision, not an incidental wiring detail. SmartLoad uses three storage classes — a time-series database (TimescaleDB), an in-memory pub/sub (Redis), and a versioned file system for models and policy. Each is chosen for a specific access pattern; using the wrong store for the wrong pattern is a design error, not an implementation detail.

Storage classes

ClassEngineUsed forWhy this engineAnti-use
Time-series TimescaleDB (PostgreSQL extension) Telemetry, derived health, scaling events. SQL expressiveness for analytics + hypertable partitioning for fast time-range queries; familiar to ML services. Don't use it for transactional state or for ephemeral signals.
In-memory pub/sub Redis Decision signals between services (anomaly, forecast, routing, policy, scale). Microsecond-latency fan-out; dependency-light; multi-language client support. Don't treat it as a persistent store. Don't use it as a key-value cache for facts that must survive restart.
Versioned files Filesystem (git for policy.yaml; gitignored for models/datasets) ML model artifacts, policy YAML, datasets, simulation traces. Reproducibility, easy diff, easy to swap into a new container build. Don't use it for high-throughput writes or shared-by-many-writers state.

Canonical schema (TimescaleDB)

-- Continuous aggregate (long-format, materialized_only=true)
CREATE MATERIALIZED VIEW metrics_1min
WITH (timescaledb.continuous, timescaledb.materialized_only = true) AS
SELECT
  time_bucket('1 minute', time) AS bucket,
  service, instance, metric_name,
  AVG(value)    AS avg_value,
  MAX(value)    AS max_value,
  MIN(value)    AS min_value,
  SUM(value)    AS sum_value,
  STDDEV(value) AS stddev_value,
  COUNT(*)      AS sample_count
FROM metrics
GROUP BY bucket, service, instance, metric_name
WITH NO DATA;

SELECT add_continuous_aggregate_policy('metrics_1min',
  start_offset      => INTERVAL '1 hour',
  end_offset        => INTERVAL '2 minutes',
  schedule_interval => INTERVAL '1 minute',
  if_not_exists     => TRUE);

SELECT add_retention_policy('metrics_1min', INTERVAL '30 days', if_not_exists => TRUE);

P95 is intentionally not computed in the CAGG. PERCENTILE_CONT is an ordered-set aggregate which TimescaleDB CAGGs reject; engines and dashboards compute P95 on raw metrics over a bounded window (cheap at SmartLoad scale). The materialized_only=true flag means queries against the view see materialised data only; the [-2 min, now] window is only visible via raw metrics — anomaly-detector and RL state queries continue to read raw, which is the design intent.

Why this schema (rationale)

  • Wide-narrow telemetry. One row per metric reading (key/value form) keeps the schema stable as new metrics are added — no ALTER TABLE on every new feature. The trade is denormalization: queries with many metrics need to join or pivot.
  • String status column instead of an ENUM. Acceptable for the prototype; an ENUM would tighten correctness but couples schema migrations to model changes. The V1 design proposes ENUMs (see comparison).
  • No FK constraints between hypertables. TimescaleDB hypertables don't compose well with cross-hypertable FKs; the schema relies on shared column conventions (backend_id, instance) instead.
  • Indexes match the canonical query patterns in services/shared/queries.py (anomaly window query, forecast window query, RL state query). Index choices are informed by query, not by guesswork.

Redis as a control bus (storage rules)

  • Redis is configured save "" + appendonly no: no disk persistence. The control bus assumes message loss is possible.
  • Subscribers must tolerate missed messages (publishers always re-publish on the next cycle).
  • Channel naming is smartload.<topic> with no .v1 suffix in the canonical wiring (per services/shared/contracts.py). The versioned form (smartload.<topic>.v1) appears in the API Design draft and is deferred until contract evolution requires it.
  • Maximum memory is bounded (maxmemory 256mb + allkeys-lru); sustained backlog will evict the oldest entries — pub/sub is fan-out, not a queue.

Filesystem ownership rules

  • config/policy.yaml — owned by Policy Manager. Other services may read it on startup but never write.
  • services/<svc>/models/*.pkl / policy.zip — owned by the offline training pipeline. The runtime container only reads.
  • data/datasets/ — owned by the dataset prep pipeline. Gitignored. Reproducible from versioned download scripts.
  • infrastructure/timescaledb/init.sql — owned by infra team. Re-run on every fresh deploy.

Storage anti-patterns

  • Storing decision signals (anomaly, forecast) only in Redis when they need replay or audit — escalate to TimescaleDB if needed.
  • Storing raw telemetry in Redis — Redis is fan-out, not history.
  • Adding a NEW table without updating infrastructure/timescaledb/init.sql + services/shared/queries.py.
  • Caching authoritative state (e.g., policy) in process memory without a refresh path on Redis publish.
  • Exposing internal schema directly to external clients via REST. Always project through a documented API shape.

Review Checklist — Storage & Schema

  • Is the chosen storage class right for the access pattern (time-series vs ephemeral vs versioned files)?
  • Does the table have only one writer (a single service)?
  • Are query indexes informed by the canonical queries in services/shared/queries.py?
  • Are retention and growth bounded (hypertable retention or LRU eviction)?
  • Are schema changes versioned (init.sql + matching contract update)?
  • Does the design tolerate Redis restart (no reliance on Redis as a persistence layer)?

11. Interface & Contract Authority

Canonical Design Intent

Every service interaction in SmartLoad is one of three contract types: a Redis pub/sub message, a REST endpoint, or a SQL query constant. There is no fourth. Contracts are typed and versionable — there is no ad-hoc JSON, no inline SQL outside queries.py, no cross-service imports of internal code. This section is the authority on what every contract should look like.

Supersession Notice — read this before SmartLoad_API_Design.pdf

The original SDP-era SDP/SmartLoad_API_Design.pdf is historical. It is a design draft predating implementation. This section (§11) and the per-module §8.x deep dives are the authoritative contract source. Where the PDF and this SOT disagree, this SOT wins. Major intentional deviations from the PDF — each documented in its module section:

  • REST API shape: single-document /api/v1/policy (GET/POST) instead of the PDF's multi-policy /api/v1/policies/{id}/activate. SmartLoad has one active policy at a time; the multi-policy model was scope creep. See §8.9.
  • No /internal/v1/* namespace. Services coordinate via Redis pub/sub (5 canonical channels below); the PDF's internal REST namespace was rejected in favour of the pub/sub control bus to keep coupling loose. See §8.10.
  • Channel naming: no .v1 suffix. PDF proposes smartload.<topic>.v1; current canonical is unsuffixed (smartload.anomaly, etc.). Deferred — see §15.
  • Envelope shape: leaner. PDF envelope has schema_version, message_id, type, emitted_at, source.service; the wired envelope (services/shared/contracts.py::Envelope) has event_id, source, version, timestamp, payload. Functionally equivalent, less verbose. See §15.
  • No backend registry REST. PDF has /api/v1/backends + /quarantine + /restore; the running system uses Docker SDK + NGINX upstream as the implicit registry. Manual override flows are covered by the T1.4 / OUI.5 endpoints (POST /api/v1/scale, POST /api/v1/isolate). See §8.8.
  • No /api/v1/experiments surface. Benchmarking is offline and CI-driven (issues #36–#39, #117), not REST-controlled.
  • Operator UI: PDF §11.5 listed a "Rich operator UI with full runtime control" as a future extension. As of 2026-05-13 this is in scope as a lightweight UI — transparency + override layer, not full runtime control. See §8.11 + issues #119–#125.
  • Error format: current responses use {error, field}; PDF mandates RFC 7807 Problem Details ({type, title, status, detail, instance}). Adoptable; left for the canonical doc landing under issue #53.
  • Adopted from PDF as-is: TimescaleDB + raw/aggregate tables, Redis pub/sub for decision signals, channel-per-topic separation, the decision-merge hierarchy (anomaly → policy → RL → classical → forecast drives scaling), one active policy with safe-mode override, OTLP/HTTP-JSON telemetry ingest.

The reconciliation work that produces the canonical external API doc (docs/api/api-v1.md) is tracked under #53. Once that doc lands, the PDF is officially retired — keep it in the repo only for historical / SDP-grader context.

Canonical message envelope

Every Redis message carries the same four envelope fields, regardless of channel. Payload-specific fields (anomaly score, predicted RPS, etc.) are added on top.

{
  "event_id":  "uuid-v4",                  // unique per publish; enables dedup
  "source":    "anomaly-detector",         // publisher service name (kebab-case)
  "version":   1,                          // envelope schema version (int)
  "timestamp": "2026-05-04T10:23:00.123Z", // RFC 3339 UTC
  "payload":   { ... }                     // typed dataclass body
}
FieldTypeWhy required
event_idUUID v4 stringSubscribers MAY deduplicate by ID. Without it, retries and re-publishes are indistinguishable from new events.
sourcestring (service name)Auditability. A publish on the wrong channel by the wrong service is detectable.
versionintegerEnvelope evolution. Bumped only when envelope semantics change, independent of the channel suffix.
timestampISO 8601 UTCStaleness detection. Subscribers reject messages older than a channel-specific TTL.

Envelope rules

  • Wrap, don't flatten. Payload fields live inside payload, not at the top level. This lets the envelope evolve independently of payloads.
  • No request/reply — pub/sub is one-way fan-out. If a request/reply pattern is needed, use REST.
  • No "command" channels. Channels publish state or events, not commands. The LB Sidecar decides how to act on a state observation; it is not commanded by the engines.
  • Idempotency by event_id — every consumer must handle re-publishes correctly. Engines re-emit on every cycle; consumers dedup by event_id if order matters, or simply use the latest timestamp if order doesn't.
  • Reject silently outdated payloads. If now() - timestamp > channel_ttl, drop the message. Default TTLs: anomaly 30 s, forecast 180 s, routing 30 s, policy never expires.

Canonical SQL access

  • FORECAST_QUERY — Forecasting Engine reads (request-rate time series, minute-bucketed).

Canonical SQL parameterization rule

Time windows and any other dynamic SQL value must be passed as parameterized values, never via Python string formatting. The correct shape for an interval is:

# Correct — parameterized, safe, cache-friendly
ANOMALY_QUERY = """
    SELECT instance, metric_name, AVG(value), MAX(value), STDDEV(value), COUNT(*)
    FROM metrics
    WHERE time > NOW() - %s::interval
      AND service = %s
      AND metric_name = ANY(%s)
    GROUP BY instance, metric_name
    ORDER BY instance, metric_name;
"""

cursor.execute(ANOMALY_QUERY, ('60 seconds', 'load-balancer', ['request_latency_ms', 'error_rate']))

The earlier .format(window=...) pattern is forbidden because (a) it bypasses parameterization, (b) PostgreSQL cannot cache the prepared plan when the query text varies, and (c) it leaks an unsafe-shaped construct into a security-sensitive area even when the values aren't user-controlled today.

Canonical service filter rule (anomaly query)

The anomaly query takes service as a parameter rather than hardcoding 'load-balancer'. This lets the same engine reason about backend-emitted telemetry once backends start emitting OTLP directly. The default operator setting is still 'load-balancer'; the parameter just keeps the design extensible.

Versioning rules (canonical)

  1. Additive change is free. Adding an optional field to a message or REST response is non-breaking. Subscribers must ignore unknown fields.
  2. Removal or rename is breaking. Either ship a new channel/endpoint version, or coordinate a synchronous cutover with all consumers.
  3. Semantic change is breaking even if the field name is unchanged. If score changes meaning, version it.
  4. The contracts.py file is the single source of truth. Tests must import from there, not redefine.

15. Routing & Decision Authority

Canonical Design Intent

Routing is the only decision the LB makes per request. Every input that influences routing is pre-computed off the request path. The hierarchy below is the safety contract that lets RL be trusted at all: anomaly always constrains, policy can always short-circuit, RL is advisory inside the bounds set by the first two, and classical is always available as the deterministic floor. This order is law (principle 9).

Canonical routing decision hierarchy

The Decision Layer is a coordinated multi-intelligence controller — not an algorithm selector. Engines run in parallel on the same telemetry; their outputs are merged through a strict hierarchy enforced by the LB Sidecar:

  1. Anomaly constraints — remove or down-weight UNHEALTHY backends from the action space. Always applied first; cannot be overridden.
  2. Active policy constraints — apply safe_mode, min_backends/max_backends limits, SLO targets. Policy can short-circuit RL but cannot override anomaly exclusion.
  3. RL routing scores — when available and permitted (mode=active), set NGINX upstream weights from RoutingRecommendation.server_rankings.
  4. Classical fallback — round-robin / least-connections always available if RL is missing, warming up, or stale.
  5. Forecasts — drive scaling decisions, not per-request routing.

Architectural meaning of the hierarchy

LevelWhy it sits at this position
Anomaly firstHard safety constraint. Routing to a known-bad backend has unbounded cost (timeouts, errors, cascading failure). The cost of incorrect exclusion (slightly underutilizing a borderline backend) is bounded.
Policy secondThe operator's veto. safe_mode is the human-in-the-loop kill switch; it must dominate any AI signal. But the operator did not cause the bad health, so anomaly remains in force.
RL thirdRL is an optimization within already-safe bounds. It is allowed to influence weights, never to authorize routing to an excluded backend or to cross policy limits. RL operates on a curated action space, not the raw set of backends.
Classical floorDeterministic, well-understood, dependency-free. If everything else fails or is silent, the LB serves traffic correctly. Classical is also the comparison baseline for benchmarks — it is never deprecated.
Forecasts off the routing pathForecast error must not corrupt routing fairness. A bad prediction should at worst cause poor scaling, never a single bad request decision.

16. Control Plane vs Data Plane

Canonical Design Intent

The deepest architectural commitment in SmartLoad. The data plane serves traffic; the control plane decides how traffic should be served. They communicate only through the LB Sidecar's config-write boundary. Mixing the two is the single biggest risk to a middleware project; this section is the rule that prevents that mixing.

Definition

PlaneMembersJobAllowed to doForbidden from doing
Data plane NGINX, backend pool Receive client requests, forward to a backend, return responses, append a JSON access log line per request. Read its loaded config; respond to graceful reload; passive health checks; write access log to stdout + shared volume. Make any network call beyond the backend it's forwarding to. Read TimescaleDB. Read Redis. Connect to the OTel Collector. Block on policy or AI service.
Control plane lb-otel-shipper, Telemetry Service, Anomaly Detector, Forecasting Engine, RL Engine, Autoscaler, Policy Manager, LB Sidecar Observe the system, decide on routing constraints / weights / capacity, push the resulting config into the data plane. Read TimescaleDB, publish/subscribe Redis, call REST endpoints, call Docker SDK, regenerate NGINX config files, tail data-plane log files. Sit on the request path. Block request flow. Be a single point of failure for traffic serving.

The boundary: LB Sidecar as config-writer

The Sidecar is the only process that crosses the planes. It sits in the control plane (subscribes to Redis, reads policy) and writes a single artifact (nginx.conf) that the data plane consumes. Once the file is written and nginx -s reload is signaled, the control plane retreats — NGINX continues serving on its own.

Why this split matters

  • Latency isolation. Slowness in the control plane (e.g., a stuck Redis subscriber) cannot slow down request serving.
  • Failure isolation. A crashed RL engine, a stalled anomaly detector, or a broken Redis instance does not stop traffic.
  • Replaceable intelligence. Engines can be swapped, redeployed, or scaled independently. The data plane sees only the resulting config.
  • Operability. Operators can disable the entire control plane (safe_mode + stop AI services) and the data plane still serves traffic with the last good config.

Common violations to refuse

  • An LB plugin that calls a Python service per request to ask which backend to pick.
  • An RL engine that proxies traffic itself ("RL gateway") instead of emitting a recommendation for the LB.
  • A "fast path" that lets one engine modify NGINX config directly, bypassing the Sidecar.
  • Telemetry collection that synchronously confirms persistence to TimescaleDB before returning a response (couples write throughput to request latency).
  • Policy reads that block the request path until the latest version is fetched.
  • Sidecar logic that performs ML inference (the Sidecar must be a thin merge + render function only).

Review Checklist — Plane Discipline

  • Can every component be unambiguously labeled "data plane" or "control plane"? Ambiguous components must be split.
  • Can the data plane serve traffic with the entire control plane stopped (last-known-good config)?
  • Does any data-plane component make a network call to any control-plane component on the request path? If yes, this is a violation.
  • Is the LB Sidecar the only component that writes nginx.conf or signals NGINX?
  • Does any control-plane component proxy or transform actual request bytes? If yes, redesign.
  • Do failure modes preserve plane isolation (a control-plane crash never blocks a request)?

21. Architecture Review Checklists

Canonical Design Intent

This section is the master review tool for SmartLoad. Every checklist below is derived from the System Design Principles (§4) and the section it serves. Use these checklists when reviewing teammate PRs, when evaluating proposed redesigns, when prompting an AI agent to generate code, or when comparing a real implementation to the canonical design.

How to use these checklists

  • For PR review. Pick the checklist that matches the area touched (routing, storage, contract, etc.). A failed item is not necessarily a blocker — but it must either be fixed or recorded as a knowing tradeoff in the PR description.
  • For proposed designs. Run the relevant checklists before code is written. A design that fails three or more items is a redesign, not a refinement.
  • For AI prompting. When asking an AI agent to implement a feature, paste the relevant checklist into the prompt and ask the agent to address each item explicitly.
  • For ongoing audit. Periodically (every release / sprint), walk every section's checklist and update §18 Build Status with what fails today.

Whole-system review checklist

Apply this when reviewing any non-trivial change.

  • Plane discipline. Does the change preserve data-plane / control-plane separation (§16)?
  • Single writer. Does the change introduce a second writer to any data class (§9)?
  • Contract surface. Is every cross-service interaction a typed contract (Redis, REST, or SQL constant) (§11)?
  • Graceful degradation. Does the change preserve the ability to fall back to classical routing (§4 principle 4)?
  • Routing hierarchy. If the change touches routing, does it preserve the anomaly→policy→RL→classical order (§15)?
  • Replaceable engines. Could the affected engine be swapped to a different algorithm without touching consumers (§4 principle 6)?
  • Observable. Does the change emit structured logs and OTel metrics? Does it have a meaningful /health?
  • Versionable. Are field additions backward-compatible? Are removals or renames coordinated through versioning?
  • Stateless on the request path. Does the change introduce per-request state in NGINX or the Sidecar (§4 principle 7)?
  • Bounded growth. Are new persistent stores covered by retention or eviction?

Routing change review checklist

  • Are anomaly constraints applied before any RL weight?
  • Is safe_mode immediate and effective on this code path?
  • Is the LB Sidecar the only writer of nginx.conf?
  • Does the change preserve classical routing as the dependency-free fallback?
  • Does the change keep forecast values out of routing decisions?
  • Is the routing decision auditable from logs?

Engine (anomaly / forecasting / RL) review checklist

  • Does the engine read only through canonical SQL constants (queries.py)?
  • Does the engine publish only its own canonical channel?
  • Does the engine subscribe to smartload.policy and react to safe_mode?
  • Does the runtime container exclude training data and training code?
  • Does the engine have a fallback for missing model files (skeleton mode)?
  • Are model artifacts loaded once at startup, not per cycle?
  • Is the cycle latency bounded and observable (metric per cycle)?

Storage / schema review checklist

  • Is the storage class right for the access pattern (time-series vs ephemeral vs versioned)?
  • Is there exactly one writer per table / channel / file?
  • Are indexes informed by the canonical query patterns?
  • Are init.sql + queries.py + tests updated together?
  • Is retention or eviction defined?
  • Does the design tolerate Redis restart?

Contract / interface review checklist

  • Is every Redis message a typed dataclass in contracts.py?
  • Is every consumer tolerant of missing or stale messages?
  • Does the change rename or remove a field? If yes, is it versioned?
  • Are REST errors shaped like the canonical Problem Details target?
  • Is every /health actually testing dependencies?

Deployment / infrastructure review checklist

  • Is every service containerized with a single Dockerfile and reproducible build?
  • Is every dependency declared explicitly (no implicit volume mounts)?
  • Does docker-compose up from a clean clone produce a green stack?
  • Is every service's image tagged and pushed by CI?
  • Are all secrets sourced from config/.env (never committed)?
  • Can the stack survive a restart of any single container?

Testing & verification review checklist

  • Does the change have unit tests for pure logic?
  • Does it have an integration test that exercises Redis + TimescaleDB end-to-end?
  • Are KPIs measurable from existing telemetry (no new instrumentation needed)?
  • Can the change be benchmarked against B1 (steady), B2 (burst), B3 (degraded backend)?
  • Are negative cases covered (missing model, dead Redis, slow backend)?

"Is this still middleware?" smell test

If too many of these are true, the project is drifting away from middleware identity:

  • The LB or Sidecar is starting to know about specific user-facing features.
  • An engine is starting to handle requests directly.
  • The control plane is becoming a single point of failure for traffic.
  • Operators must restart the LB to apply policy changes.
  • Engines have started importing each other's modules.
  • Database schema has started encoding business logic instead of telemetry.
  • Tests are stuck behind elaborate mocks that don't reflect the real Redis / TimescaleDB.

Why something from it should be preserved: The depth of ML treatment per module (the per-engine subsections in the original plan) is still useful as scope material for §6 deep dives in this document.

What they were: Two parallel milestone-based plans authored as alternatives to the 10-sprint plan.

Why they were rejected: Same advisor directive. The integration-first reframing made both obsolete simultaneously.

Status: Historical. Kept for provenance only.

Draft (revisit later): V1 6-table schema (V1__smartload_schema.sql, May 4, 2026)

What it is: Richer 6-table schema with backend_nodes, policies, telemetry_metrics (explicit columns), routing_decisions, anomaly_events, scaling_events, plus 8 ENUM types, retention policies, continuous aggregates, and 7 days of seed data.

What it does well: Tighter type safety (ENUMs over TEXT), continuous aggregates for fast dashboards, explicit columns for the canonical metric set, retention policies baked in. Closer to a production schema.

What's weak today: Schema-rigid — every new metric requires ALTER TABLE. routing_decisions introduces a write source on or near the request path; placement needs care so the data plane stays pure. Migration from the canonical 3-table schema is not yet planned.

Why current canonical is preferred: The 3-table wide-narrow schema is wired and validated by 33 integration tests. Lower friction during the active research phase.

Recommendation: Revisit Phase 2 review. Once the metric set stabilizes, V1 becomes the strong target schema. Migration must include a backfill plan and re-validation of queries.py.

Draft (revisit later): SmartLoad Feature Contracts (Mar 27 DOCX)

What it is: Per-module ML feature contracts — input features, output schema, training schedule for each AI engine.

What it does well: Forces every engine to commit to its feature surface up front; would prevent feature creep.

What's weak today: Authored before integration-first reframing; assumes engines were further along than they are. Some features assume a richer schema (V1) that is not yet adopted.

Recommendation: Revisit alongside V1 schema. Adopt as a Phase 2 deliverable once V1 schema is reviewed.

Draft (revisit later): SmartLoad Service Contracts (Mar 28 DOCX) — SLA targets

What it is: Client / Backend / Operator SLAs including 99.5% availability, HTTP 207 multi-status semantics for partial backend failure, etc.

What it does well: Production-shaped commitments. Operationalizes principle 10 (prototype realism with production ambition).

Recommendation: Confirm scope. Adopt SLO targets as canonical even if availability targets are aspirational. Defer HTTP 207 to a future iteration with explicit scope.

SmartLoad is not "an NGINX product." 25.6 Plugin-per-folder convention

Inside each AI service, replaceable strategies live one folder per plugin under engines/ or policies/:

  • services/anomaly-detector/engines/threshold/, engines/isolation_forest/
  • services/forecasting/engines/moving_average/, engines/arima/
  • services/rl-engine/policies/random_shadow/, policies/ppo/

Each plugin folder is self-contained: engine.py implementation, README.md describing rationale + fallback, and per-plugin test_engine.py. The factory in engine_base.py / policy_base.py selects the plugin from an env var; missing model files fall back to the baseline plugin without service restart. This is the design that lets a model author drop an isolation_forest.pkl into models/ and have the service swap engines with no code change in the service shell. Issue #138 wires the engine factory into the service run loop.

Engine bootstrap with safety-net fallback

At service startup, the run loop resolves the engine through a strict bootstrap sequence. If the requested engine fails to load — missing artifact, bad name, exception in __init__ — the service falls back to the named baseline (threshold / moving_average / random_shadow) and reports engine_ready=false on /health. The baseline itself is the safety net: if even it fails, startup raises, because that's a deployment bug and silence would mask it.

Run-loop cycle (per service, identical shape)

Once bootstrapped, each AI service runs a single thread that interleaves Redis pub/sub message handling and tick-based inference. The pubsub get_message uses a 1-second timeout so policy updates land within one second; between messages, the loop runs an inference cycle every POLL_INTERVAL_SECONDS. Engine reconstruction on policy change keeps trained-model loading cheap (cached artifact) while honouring policy-derived constructor kwargs.

Model author handoff boundary

The diagrams above are the integration layer's contract. A model author owns only the boxed step — the engine class with its score() / forecast() / act() method, plus the trained artifact at services/<svc>/models/<name>.pkl. The Redis publish, the DB query, the policy reload, the fallback path, the health reporting, the unit-test scaffold — all owned by the integration layer. This is the boundary the PR #144 review codified.

Idempotency

POST /api/v1/policy is idempotent on body equality: posting the same patch twice produces one audit row, one envelope publish, and one policy_version bump. The second POST returns {status: "no-op", changed_fields: []}. Operators may safely retry without producing audit noise.

26.7 Versioning and deprecation Issue #134

  • Path versioning only. /api/v1 today; /api/v2 when a breaking change ships. No header- or query-string-based version negotiation.
  • Compatibility window: a deprecated version stays reachable for at least one calendar quarter after a successor ships.
  • Deprecation signal: every response from a deprecated endpoint carries Sunset: <date> and Deprecation: true.
  • Breaking change definition: removing a field, narrowing a type, renaming an enum value, changing default values, or moving a field from optional to required.
  • Non-breaking: adding a new optional response field, adding a new endpoint, adding a new optional request field.

27.4 Event subscriptions — model and lifecycle

import threading

with SmartLoadClient(base_url="http://localhost:8086") as c:
    received = []
    arrived  = threading.Event()

    def on_update(payload, meta):
        received.append(payload)
        arrived.set()

    sub = c.subscribe_policy(on_update)
    try:
        # Drain pre-attach backlog if relevant (cooperating tests).
        # The SDK does not auto-drain because the right policy is
        # caller-specific.
        c.set_policy({"safe_mode": True}, actor="my-tool")
        arrived.wait(timeout=5.0)
        print("envelope received:", received[-1]["policy_version"])
    finally:
        sub.close()
  • Channel TTL: the SDK applies the canonical per-channel TTL (§11). Stale messages are dropped before the callback runs.
  • Redis disconnect: if the underlying socket drops, the SDK logs and retries with a 1 s backoff. For long-running subscribers, monitor the smartload_client logger.
  • Threading model: one daemon thread per subscribe_* call. Several active subscriptions are fine; close them when done.
  • Backlog before attach: pub/sub is not durable. Messages published before subscribe_policy is called are not delivered.

BFF data flow

The operator-UI BFF process holds the entire Live Engines state machine; the AI services are unaware that a UI exists.

  1. One daemon thread per process (lazy-started on first /api/ui/engines/* request) subscribes to smartload.{anomaly,forecast,routing,scale} via the canonical shared.contracts.subscribe_envelope helper. Stale messages (per channel TTL — anomaly/routing 30 s, forecast 180 s, scale never) and malformed envelopes are dropped at the parser; valid ones become the canonical entry shape {channel, envelope:{event_id,source,version,timestamp}, payload}.
  2. Each entry is appended to a per-channel collections.deque(maxlen=100) (the ring buffer) and broadcast to every connected SSE subscriber's bounded queue.Queue(maxsize=256).
  3. A slow SSE client whose queue is full has events silently dropped for that client — the ring buffer still has them; back-pressure to the publisher would compromise the design. The subscriber loop never blocks.
  4. On Redis disconnect, the loop catches the exception, sleeps the reconnect delay, and rebuilds the subscription. The ring is preserved (in-process state); a BFF restart rebuilds the ring from the next message — no persistence required.
  5. Gunicorn worker class is gthread (2 workers × 8 threads) so a long-lived SSE connection occupies one thread, not one whole worker.

28.7 Design choices — what we explicitly didn't do

  • No iframe-Grafana. Charts are first-class UI elements (planned #131), not embedded Grafana dashboards. Grafana stays for SRE-grade ad-hoc PromQL exploration — the operator UI is for transparency and override during incidents.
  • No backend management surface (delete tenant, edit user). The UI is operator-facing, not admin-facing. SaaS-side admin tooling is a separate concern outside this SOT.
  • No client-side caching beyond the React state. Auto-refresh is the correctness model — the operator should always see fresh state during an incident.
  • SSE, not WebSocket, for the live transport. Slices #1–#3 used 10 s polling — sufficient for state that changes on operator action. The Live Engines page (#121) needs sub-second updates as envelopes land on the control bus, so it uses Server-Sent Events: one-way, Flask-native, browsers reconnect automatically. WebSocket was deliberately rejected — bidirectional capability for no client-to-server traffic, and an additional dependency.
  • BFF in-memory ring buffer, not a dedicated archiver service. The original #121 design proposed a separate services/events-archiver/ that would LPUSH envelopes into a Redis smartload:events:recent list capped at 1000 via LTRIM. The shipped design keeps the buffer inside the operator-UI BFF process (per-channel collections.deque(maxlen=100)), preserving §28's "pure read, not a SmartLoad layer" framing — engines stay unaware that a UI exists, and a BFF restart rebuilds the buffer from the next message. A durable events_log hypertable in TimescaleDB remains a deliberate Sprint 5+ stretch (see §28.5 Gap to close); the in-memory buffer is sufficient for the operator-visibility use case the page actually serves.

29.4 HMAC signing

Algorithm — HMAC-SHA256 with timestamp prefix

Modelled on Stripe's webhook signing scheme. Resists replay attacks via a timestamp inside the signed payload; resists tampering via the body hash. Customer rejects requests where the timestamp differs from now by more than a tolerance (suggested: 5 minutes).

signed_payload = "{unix_timestamp}.{raw_request_body}"
signature      = hmac_sha256(secret, signed_payload).hex()
header         = f"t={unix_timestamp},v1={signature}"
# sent as:        X-SmartLoad-Signature: t=…,v1=…
ElementNotes
unix_timestampInteger seconds, set by the dispatcher at send time. Refreshed on every retry.
raw_request_bodyExact UTF-8 byte body, no re-serialisation. The customer MUST verify against the bytes they received, not against a re-parsed JSON.
Header formatComma-separated k=v pairs. Future scheme versions add v2=… alongside v1=… for graceful rotation.
Hex caseLowercase hex. Customers may upper-case before constant-time compare.

Verification — Python

import hmac, hashlib, time

TOLERANCE_SECONDS = 300  # 5 minutes

def verify_smartload_signature(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    t   = int(parts["t"])
    sig = parts["v1"]

    if abs(time.time() - t) > TOLERANCE_SECONDS:
        return False  # too old → reject (replay defence)

    signed_payload = f"{t}.".encode() + raw_body
    expected = hmac.new(secret.encode(), signed_payload, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, sig)

Verification — Node.js

import crypto from "crypto";

const TOLERANCE_SECONDS = 300;

export function verifySmartLoadSignature(rawBody, header, secret) {
  const parts = Object.fromEntries(header.split(",").map(p => p.split("=", 2)));
  const t   = parseInt(parts.t, 10);
  const sig = parts.v1;

  if (Math.abs(Date.now() / 1000 - t) > TOLERANCE_SECONDS) return false;

  const signedPayload = Buffer.concat([Buffer.from(`${t}.`), rawBody]);
  const expected      = crypto.createHmac("sha256", secret).update(signedPayload).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected, "hex"), Buffer.from(sig, "hex"));
}

Final-failure path

  1. Final attempt fails → row written to webhook_delivery_failures.
  2. Failure counter webhook_delivery_failures_total{webhook_id, event_type} incremented (Prometheus).
  3. 50 consecutive failures within 1 h → webhook auto-suspended (state transitions to suspended). The operator must manually re-enable.
  4. Operator UI dead-letter view (planned with #122) renders the latest N failures per webhook with the response body / status for debugging.

At-least-once semantics

Customers MUST be idempotent on receipt. The same X-SmartLoad-Event-Id may arrive more than once if a retry slips past a successful-but-slow customer response. Persist the event-id in a dedup table with a short TTL (≥ 1 h).

29.6 Security considerations

  • Secret confidentiality: the secret is delivered once at registration time (in the response body). It's hashed before storage. If lost, the customer must rotate by deleting + re-registering — there is no "fetch existing secret" surface.
  • Secret rotation: the v1 signature header supports adding v2=… in the future. Customers verify against any present version; the dispatcher emits whichever is configured. Migration path: dispatcher emits both v1 and v2 for a window; customer updates verifier; dispatcher drops v1.
  • HTTPS endpoint: required for any production webhook. The dispatcher logs (and the UI surfaces) a "non-HTTPS endpoint" warning on registration.
  • IP allow-list (future): customers can request a static egress IP for SmartLoad-side outbound deliveries when the SaaS control plane lands. Not in scope for self-host.
  • Replay defence: 5-minute timestamp tolerance. Customers tighten if their integration allows; loosen only when retrying across long network partitions.
  • Body re-serialisation pitfall: customers must verify against the raw body bytes, not against a JSON re-serialisation. Any whitespace or key-ordering change breaks the hash.

29.7 Tenant + multi-tenancy

Webhook records carry tenant_id — a tenant cannot register webhooks for another tenant's events. After multi-tenancy lands (#129), the dispatcher consumes from t:<tenant_id>:smartload.<topic> per tenant; today (single-tenant), it consumes from the unsuffixed channels.

30.7 Multi-tenancy plan Issue #129

Each hypertable gets a tenant_id TEXT NOT NULL column and a composite index (tenant_id, time DESC). Indexes used by existing queries get rebuilt as (tenant_id, <original columns>). Writers stamp tenant_id at insert time; readers scope every SELECT.

PhaseWhat lands
Phase 1 — schema only Add tenant_id column (NULLABLE for one release cycle, defaulting to 'default'). Backfill existing rows. Switch index definitions to composite. Zero query changes.
Phase 2 — writers Every service includes tenant_id in every INSERT. Today's single-tenant writers default to 'default'.
Phase 3 — readers + NOT NULL Every SELECT includes a tenant_id = $X predicate. Column flipped to NOT NULL. Backfill is complete; legacy NULL rows are gone.
Phase 4 — tenants + api_keys + webhooks New tables (§30.2 planned) land. API auth middleware resolves tenant_id from the API key (#132) and stamps it on every downstream call.

Rollout sequencing avoids any moment where the database is in a half-applied state. Each phase is independently revertable.

30.8 Migration strategy

  • Source of truth: infrastructure/timescaledb/init.sql contains the full canonical DDL applied on first container start. Subsequent schema evolutions live as numbered scripts under infrastructure/timescaledb/migrations/<N>__<description>.sql (planned — migrations/ folder not yet created; first migration arrives with #129).
  • Idempotency: every migration is CREATE … IF NOT EXISTS + ALTER TABLE … IF NOT EXISTS compatible. Re-running a migration on a partially-applied database completes the operation rather than failing.
  • Application strategy: services apply pending migrations on startup (planned). For Helm deploys, a Kubernetes Job runs migrations before the rolling update of dependent services.
  • Rollback: every migration ships with a paired migrations/<N>__<description>_down.sql. Not all migrations are reversible — destructive operations are flagged in the up script's comment header.
  • Policy schema versioning: orthogonal to DB migrations. Tracked by schema_version in policy.yaml (#134). The DB doesn't enforce policy schema — policy-manager does.

30.9 Backup and restore

Self-host deployers are responsible for backup; SmartLoad does not bundle a backup orchestrator. Recommended baseline (planned — not yet enforced):

  • Compose: nightly pg_dump against the smartloaddb database. The timescaledb-data named volume is the live store.
  • Kubernetes: use the TimescaleDB Operator's continuous WAL archiving + scheduled snapshots; ship the Helm chart with a sample CronJob in infrastructure/helm/smartload/templates/backup.yaml (planned).
  • Restore drill: documented in SDP/runbooks/restore-from-snapshot.md (planned).

Audit ledgers (policy_changes, scaling_events) deserve special attention: losing them loses the "who changed what" story. For SaaS, these tables are replicated to an immutable archive.
