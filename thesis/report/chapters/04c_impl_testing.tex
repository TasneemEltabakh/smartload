\section{Testing and Evaluation}\label{ch:impl_testing}

Software that makes its own decisions about live traffic has to be checked
carefully. A bad routing or scaling choice is not a small visual bug; left
unchecked, it can take a service down. For that reason, SmartLoad treats its tests and benchmarks as
real engineering work, not an afterthought. A fast, deterministic check guards
every engine on its own, a slower live-stack check guards every pair of services on
a running cluster, and a small set of end-to-end checks guard each feature a
customer actually uses. This section lays out that test pyramid and then turns to
the two custom benchmark harnesses that answer the project's research questions,
together with the results they produced.

\subsection{Test strategy: a layered pyramid}\label{imc:pyramid}

The repository organises its checks as a classic test pyramid, plus three
structural lints that protect the repository's own conventions. The shape is
bottom-heavy on purpose. Most of the checks are fast, pure-Python unit tests that
need no Docker and no network, so the inner development loop stays in seconds. The
expensive live-stack tests are kept for the contracts that genuinely cannot be
exercised without a running cluster. \Cref{fig:imc:pyramid} draws the shape
qualitatively, and \cref{tab:imc:layers} reports the per-module unit-suite counts
collected at the audited commit, which is the layer the bulk of the testing
lives in.

\paragraph{Unit layer.} Each decision engine is a pure function of its
inputs. The threshold rule, the Isolation Forest scorer, the moving-average and
ARIMA forecasters, the PPO argmax-dominant weighting, and the autoscaler's
dead-band arithmetic all reduce to deterministic transforms, so each one can be
checked against a hand-computed expectation. These tests run with \texttt{pytest
tests/unit/} in a few seconds and gate every commit, so a change that shifts a
verdict boundary fails right away and in plain sight.

\paragraph{Integration layer.} These tests assume \texttt{docker compose up
-d} and check the contract between a pair of services on the wire. A
\texttt{stack\_ready} fixture in \texttt{tests/integration/conftest.py} blocks until
every service reports \texttt{/health} before any test runs. They cover the
telemetry OTLP ingress and database persistence, per-request latency fidelity on
live traffic (\texttt{STDDEV(latency) > 0}), the autoscaler's cooldown and reactive
fallback, the dynamic-pool \texttt{provision()}/\texttt{decommission()} lifecycle
against the live Docker daemon, and the four-channel closed-loop dispatch.

\paragraph{End-to-end layer.} The end-to-end tests drive a whole feature
through the customer-facing SDK rather than an internal seam. The adaptive-bench
compressed run, for example, drives the five-phase load shape under a 60-second CI
budget and checks that all eight raw artefacts come out with the correct schema.

\paragraph{Conformance and structural lints.} A single conformance suite
(\texttt{tests/\allowbreak conformance/\allowbreak lb\_\allowbreak adapter/}) pins the load-balancer adapter
interface. At present it exercises only the implemented \texttt{NginxAdapter}
together with an in-test mock; the ALB, Envoy, and HAProxy adapters are declared
stubs that raise \texttt{NotImplementedError} and are not yet exercised. The
suite therefore fixes the contract a future adapter would have to satisfy, rather
than demonstrating that a second back end already meets it. Three structural lints
(\texttt{scripts/\allowbreak lint-\allowbreak structure.py}, \texttt{lint-\allowbreak redis-\allowbreak channels.py},
\texttt{lint-\allowbreak openapi.py}) protect the repository's conventions rather than its
behaviour: they flag a feature document without a matching end-to-end test
directory, a Redis channel published but never subscribed, and an HTTP route absent
from the OpenAPI contract. \Cref{tab:imc:lints} states what each lint enforces and
where the drift would otherwise hide.

\paragraph{Slow tests and the acceptance pattern.} A few live-stack tests have
natural multi-minute runtimes, such as a forecast-to-scale-out cycle or a
model-calibrated detector reaching its verdict, and so they carry
\texttt{@pytest.mark.slow}, so the continuous-integration \texttt{compose-test} job
filters them out by default and operators run them on demand. Beyond the layering,
every product task ships \emph{two} test artefacts: one pure-Python unit test and
one live-stack acceptance test whose module docstring cites the specification
section it maps to. That citation is the link between the executable test and the
written contract, so a reviewer reading an acceptance test can jump straight to the
clause it enforces.

\section{Evaluation Methodology}\label{imc:methodology}

The test suite answers ``does the feature work?''. The benchmarks answer ``how well
does it work, and is it holding steady over time?''. SmartLoad's evaluation is built
around four research questions, three of which are exercised by the custom harnesses
inventoried in \cref{tab:imc:harnesses}. The \emph{adaptive-bench} measures the
closed forecast~$\rightarrow$ autoscaler~$\rightarrow$~sidecar loop (RQ4); the
\emph{baseline-vs-smartload routing bench} compares plain NGINX round-robin against
the full decision plane on an identical stack (RQ1, RQ3); and the
\emph{anomaly-engine-bench} compares the deterministic threshold rule against the
trained Isolation Forest engine across a feature grid. All three follow the same
discipline: every run writes a \texttt{MANIFEST.json} recording the timestamp, the
git SHA, the working-tree state, and every knob value, so a third party with the same
checkout and Docker host can reproduce the figures.

\subsection{The adaptive-bench harness}\label{imc:adaptivebench}

The adaptive-bench drives the live stack through a five-phase Locust~\cite{locust}
load shape, built to exercise both forecast-driven scale-out and anomaly-driven
reroute in a single repeatable command. The phases, summarised in
\cref{tab:imc:phases-plan}, are: \texttt{A\_bootstrap} (a low steady warm-up that
sets a forecast baseline); \texttt{B\_forecast\_burst} (a sharp ramp to 200 users
that the forecaster should see coming before saturation); \texttt{C\_sustain} (the
burst held while a phase-D-style anomaly is injected into one backend);
\texttt{D\_anomaly\_scale\_down} (load dropped so the autoscaler should shed
capacity); and \texttt{E\_steady} (a low steady tail that confirms the system
settles). An asyncio orchestrator runs the load shape alongside three collectors,
namely a Prometheus~\cite{prometheus} scraper at 1\,Hz, a server-sent-events collector
tailing the decision envelopes, and an upstream watcher polling \texttt{upstream.conf}
every two seconds. A phase-D injector then drives a target backend's
\texttt{/\_admin/delay} endpoint and posts a manual isolation event.

  \centering

  \label{tab:imc:phases-plan}
  \small
  \begin{tabularx}{\linewidth}{@{}l l Y@{}}
    \toprule
    \textbf{Phase} & \textbf{User target} & \textbf{What it exercises} \\
    \midrule
    \texttt{A\_bootstrap}           & $\approx$19 users  & Forecast baseline; idle single-backend pool \\
    \texttt{B\_forecast\_burst}     & 200 users          & RQ4: forecaster anticipates the ramp; autoscaler pre-warms \\

    \bottomrule
  \end{tabularx}
\end{table}

The join pipeline (\texttt{join\_run.py}) fuses the eight raw artefacts into a
per-second timeline (\texttt{run.parquet} plus per-channel parquets), and the
plotter (\texttt{plot\_results.py}) renders the four figures presented in
\cref{imc:results}. To move from single-run point estimates to publishable
statistics, the harness accepts a \texttt{-{}-runs N} flag (default five) that
launches $N$ independently seeded runs; a shared \texttt{aggregate\_runs.py} then
computes, for each phase and each metric, the mean and a 95\% confidence interval
using Student's $t$ distribution with $N-1$ degrees of freedom, drawing confidence
bands on the plots. The seed fixes only the load-generation jitter, so the leftover
run-to-run variance from cold caches, just-in-time warm-up, and container start-up is
exactly what the interval measures.

\subsection{The anomaly-engine-bench harness}\label{imc:anomalybench}

The anomaly-engine-bench is an investigation tool rather than a load test. It sweeps
a two-dimensional feature grid, with per-request latency across $[10, 600]\,\text{ms}$
and error rate across $[0, 0.2]$, and at each grid cell asks both the threshold
rule and the Isolation Forest engine for a verdict. The output is an agreement
matrix: a heatmap showing where the two engines concur and where they diverge,
together with the direction of any divergence (whether the model is more cautious
than the simple rule, or whether the rule is catching something the model treats as
normal). This harness is deliberately decoupled from the running cluster, since it
calls the engines as pure functions over synthetic features, isolating the model's
decision surface from any confounds in the live telemetry path. As shown in
\cref{imc:results}, this harness is what confirmed that the trained detector reproduces
the deterministic rule while adding extra coverage.

\subsection{The baseline-vs-SmartLoad routing bench}\label{imc:routingbench}

The routing bench answers the comparison questions directly: it runs the same
docker-compose stack twice, once with the decision plane silent and once with it
fully engaged, and contrasts the two latency distributions. Its central design
principle is to minimise hidden variables. The compose stack, the backend pool image,
the NGINX configuration, the test-backend code, and the operator-UI back-end-for-front-end
are byte-for-byte identical across the two sides. Only five environment flags differ,
and those five are exactly the switch that turns SmartLoad's intelligence on or off.
\Cref{tab:imc:protocol} reproduces the diff between the two recorded environment
profiles in \texttt{experiments/baseline-vs-smartload/env/}.

On the baseline side the decision plane is silent: the services start up and expose
\texttt{/health} but never enter their inference cycle, and the lb-sidecar does not
subscribe to Redis, so \texttt{upstream.conf} stays at the static round-robin
configuration. On the SmartLoad side the same services run their full inference cycle
and the sidecar rewrites \texttt{upstream.conf} and reloads NGINX in response to the
published envelopes. The load-balancer container itself does not read these flags and
is not restarted between sides, so the only moving part is the decision plane.

The workload is a three-phase Locust shape: a linear ramp that tests whether
forecasting drives scale-out before saturation, a hold that exposes any
heterogeneity drag, and an anomaly phase that injects a latency spike on one backend.
The anomaly is modelled as a slow-but-healthy backend that still returns
\texttt{200 OK}, chosen precisely so NGINX's passive \texttt{max\_fails} health check
cannot trivially solve the problem. That keeps the comparison fair: plain round-robin
keeps dispatching a fifth of its traffic to the slow backend, which is the failure
class the anomaly and lb-sidecar pipeline is designed to address. The honest finding
this bench produces is discussed in \cref{imc:theory}.

\subsection{Computer-based tools and statistics}\label{imc:tools}

The evaluation leans on standard, reproducible tooling rather than bespoke
measurement. Load is driven by Locust~\cite{locust}; system state is scraped from
Prometheus~\cite{prometheus} exposition endpoints; raw frames are stored as columnar
Parquet and joined with the \texttt{pandas}/\texttt{pyarrow} stack; plots are
rendered with \texttt{matplotlib}. Statistical reporting uses the Student's $t$
confidence interval described above for the multi-run case, and the anomaly-engine
comparison reports an agreement rate as a simple proportion over a fully enumerated
grid (so the whole population, not a sample, is measured, leaving no sampling
error to bound).

\subsection{Anomaly engine: the trained detector tracks the rule}\label{imc:results_anomaly}

The anomaly-engine-bench compares the trained Isolation Forest engine against the
deterministic threshold rule across a fully enumerated feature grid. This sweep
sets the trained detector against the stateless reference rule; it is not the
deployed-engine selection, since the production default is the stateful
\texttt{trend\_rule} (\cref{imb:threshold}), and the threshold rule here is the
calibration reference rather than a shipped default. The Isolation Forest model
was trained on the Server Machine Dataset~\cite{su2019omnianomaly} and scores
F1\,$=$\,\BMifFone{} on the held-out split, clearing the project's $>0.80$

\section{Comparison to Theoretical Predictions}\label{imc:theory}

A benchmark is only as valuable as the prediction it tests. This section sets the
measured behaviours against the analytic expectations from the design chapters. In
each case the system behaved as the design predicted, including where that prediction
is that a learned policy ties its classical baseline.

\paragraph{Pool size versus the capacity model.} The autoscaler's design predicts a
target instance count of $n = \lceil \hat{r} / c \rceil$, where $\hat{r}$ is the
predicted request rate and $c$ the per-backend capacity, with a dead band
$[(n{-}1)c,\, nc]$ damping oscillation around the boundary, and the pool is hard
capped at the policy's \texttt{max\_backends}. The observed trajectory matches this
prediction in shape: the pool grows as the forecast burst pushes $\hat{r}$ across
successive band ceilings, saturates at the configured cap when offered demand
exceeds what the capped pool can serve, and contracts symmetrically as load falls
(\cref{fig:imc:pool}). The scaling actions line up with band crossings rather than
flapping, so the dead band and cooldown do their job. The match is structural, not
coincidental: the autoscaler is a direct implementation of the ceiling rule. The
realised pool range and scaling-action count for this run are regenerated from the
fresh benchmark batch.
% TODO(vps-rerun): pool range + scaling-action count tying capacity model to observed trajectory, from fresh VPS run

\paragraph{Forecast-driven scale-out and scale-in.} The design predicts that the
forecaster anticipates a rising load and the autoscaler pre-warms capacity before
saturation, then sheds it as load falls. Both halves occurred exactly as predicted.
The scale-out arrived during the forecast burst and sustain phases, and the scale-in
followed cleanly on the scale-down phase, settling without flapping in the steady
tail. The closed loop behaved end-to-end the way the design said it would.

\paragraph{Anomaly agreement versus the deterministic rule.} The Isolation Forest
engine was expected to reproduce the threshold rule's verdicts on the cells where the
rule is clearly right, while adding sensitivity on the cells where a single static
cut-off is too blunt. The \BManAgree{} agreement with zero relaxed verdicts is exactly that
prediction realised: the model is a strict superset of the threshold rule's caution,
and the residual disagreements all lie in the direction of catching additional signal.

\paragraph{Learned routing versus round-robin.} On the \emph{open-loop} evaluation
the trained PPO routing policy \emph{matches} NGINX round-robin: both record an
identical \texttt{mean\_reward} of \BMrlPpoReward{} and a zero SLO-violation rate, because
the policy was trained on traces whose per-backend latencies are homogeneous at around
9.7\,ms, all well below the 200\,ms SLO. On a homogeneous pool the optimal routing
policy \emph{is} uniform spread, since there is no faster backend to prefer, so the
policy correctly learned round-robin equivalence. That tie, though, is a tie on a
simulator that cannot tell routing policies apart. The closed-loop benchmark, which
lets a routing choice affect the next state, does separate them, and there the
trained policy is the \emph{worst} of the contenders: the deployed \texttt{monotone}
heuristic violates the objective on \BMrlMonoSla{} of the run, round-robin on \BMrlRrSla{}, and
the shipped PPO policy on \BMrlPpoSla{}. For that reason the deployed router is the
deterministic \texttt{monotone} heuristic, and the trained policy is pinned to
\texttt{shadow} mode as a dormant comparator that produces a parallel, auditable
decision stream while it earns nothing on the live path. The binding constraint is
named plainly: the routing acceptance gate (a clear delta on at least three of five
metrics) is currently \emph{red} on this PPO model, and closing it requires retraining
on a heterogeneous-latency distribution, under a closed-loop simulator, before a
learned policy could be considered for promotion to \texttt{active}.

\paragraph{The cost of an active rewrite.} The routing bench also surfaces a cost
that the project reports rather than hides. On the heterogeneous run the per-phase
p95 figures track closely between the two sides, but the single maximum latency across
the run is higher on the SmartLoad side than on the baseline side. That gap is not a
routing regression; it is the lb-sidecar's NGINX-reload cost during the anomaly
window, the brief connection blip an \texttt{upstream.conf} rewrite incurs. It is
included unfiltered because suppressing it would misrepresent the trade-off between a
static configuration and a reactive one. The exact maximum-latency figures for each
side are regenerated from the fresh benchmark batch.

\paragraph{A broader head-to-head.} A planned, broader head-to-head benchmark would
compare SmartLoad against plain round-robin across additional, more heterogeneous
workloads, quantifying end-to-end latency and failure-rate behaviour at full run
length with 95\% confidence intervals. This is a deliberate next step on the roadmap,
building on the harness and statistics already in place.

\section{Standards and Best Practices in the Implementation}\label{imc:standards}

SmartLoad's engineering rests on widely adopted standards rather than bespoke
conventions, both to keep the system interoperable and to keep its claims auditable.
The most concrete evidence is the following.

\begin{itemize}
  \item \textbf{OpenAPI-linted HTTP contract.} Every service's REST surface is
        described in an OpenAPI~\cite{openapi} document, and a structural lint
        (\texttt{lint-openapi.py}) fails the build when a route exists in code but
        not in the contract, so the published interface and the running interface
        cannot quietly drift apart.
  \item \textbf{OTLP telemetry.} The load-balancer shipper emits per-request
        telemetry as OpenTelemetry~\cite{opentelemetry} OTLP/HTTP-JSON through a
        collector, the vendor-neutral standard for observability data, rather than a
        proprietary wire format.
  \item \textbf{Prometheus exposition.} Every service exposes a Prometheus
        \cite{prometheus} \texttt{/metrics} endpoint in the standard exposition
        format, which the benchmark collectors and the operator dashboards both
        scrape without service-specific adapters.
  \item \textbf{The engine-authoring contract.} New decision engines implement a
        single documented interface (the pluggable-engine pattern of
        \cref{ch:impl_decision}), so a threshold rule, an Isolation Forest, or a
        future model are interchangeable behind the same contract, while the
        conformance suite pins the load-balancer-adapter interface against the
        implemented NGINX adapter and a mock.
  \item \textbf{The per-task acceptance-test pattern.} Each task ships a unit test
        and a live-stack acceptance test whose docstring cites the specification
        clause it enforces, making the spec-to-test link explicit and reviewable.
  \item \textbf{Structural CI lints.} Three lints protect the repository's own
        invariants, namely feature-to-test coverage, Redis channel publish/subscribe
        symmetry, and OpenAPI completeness, catching documentation and contract
        drift mechanically rather than relying on reviewer vigilance.
  \item \textbf{Semantic versioning.} Releases follow a disciplined version cadence
        with a per-work-unit suffix bump, and each release row in the project's
        source of truth records its commit SHA, so any reported number is traceable
        to the exact code that produced it.
\end{itemize}

Taken together, these practices mean that SmartLoad's results are not just measured
but \emph{reproducible}: a reader with the recorded git SHA, the same Docker host,
and the verbatim environment profiles can re-run a harness and get the same figures,
which is the standard the project holds itself to.
