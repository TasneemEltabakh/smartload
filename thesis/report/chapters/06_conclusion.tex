\chapter{Conclusion}
\label{ch:conclusion}

This report set out to design, build, and evaluate a load-management middleware that
schedules capacity ahead of demand rather than reacting after the fact, while staying
safe enough to sit in the request path of a production service. This chapter recaps the
problem and solution, states the headline results, reflects on what we learned, and lays
out a roadmap. It keeps the project's framing throughout: report each result as it is and
let the engineering reasoning behind each decision stand on its own.

\section{Summary of the Proposed Solution and Results}
\label{conc:summary}

\paragraph{The problem.} Conventional infrastructure couples three problems that
compound under load. Autoscaling is \emph{reactive}: capacity is added only after a
saturation signal has already degraded service. Routing is \emph{static}: a round-robin
or least-connections scheduler ignores which backend is healthy or fast right now, so a
single slow instance taxes a fixed fraction of every request stream. The obvious remedy,
inserting learned models to predict demand, detect anomalies, and route adaptively,
raises a third problem: an opaque model that misfires in production needs a floor
beneath it before operators will put it on the critical path.

\paragraph{The solution.} SmartLoad addresses these as a single proactive control loop
of the three planes described in \cref{ch:design_solution} and \cref{ch:impl_overview}.
An NGINX \emph{data plane} carries traffic and emits per-request telemetry. A
\emph{decision plane} of three engines (demand forecasting, anomaly detection, and
learned routing) turns that telemetry into predict-ahead decisions, which a
\emph{control plane} of an autoscaler, a policy manager, and a load-balancer sidecar
actuates by provisioning capacity and rewriting the upstream configuration. The planes
communicate over a five-channel Redis bus, so each component is decoupled and
independently testable. The defining discipline is that \emph{every learned model has a
deterministic fallback beneath it}: a moving-average forecaster, a threshold anomaly
rule, and a classical round-robin scheduler, with an operator override above the whole
loop. This is what makes a learned stack safe to ship, because the system degrades to a
well-understood baseline the moment any model is absent, slow to load, or switched off,
without losing safe behaviour.

\paragraph{The results.} The mechanism is demonstrated end to end. The loop closes
because the configuration and actuation chain is wired correctly and because the
deterministic capacity-aware heuristic and the classical scheduler do the live work, not
because any learned model drives the path. That deterministic floor is what lets each
learned engine sit in the live path safely. The detailed reading is in
\cref{ch:impl_testing} and \cref{ch:discussion}; the consolidated result follows.

\begin{itemize}
  \item \textbf{Closed-loop proactive autoscaling works.} In the committed adaptive
        benchmark run, a forecast-driven burst grew the backend pool from its idle
        baseline to the configured capacity ceiling and contracted it as demand receded,
        with time-to-react on the order of seconds. The
        forecast~$\rightarrow$~autoscaler~$\rightarrow$~sidecar loop closes against a live
        stack, the affirmative answer to the project's proactive-autoscaling question.
        % TODO(vps-rerun): verified pool range + scaling-action count from fresh VPS adaptive batch
  \item \textbf{The deployed anomaly engine closes the gradual-degradation gap.} The
        shipped \texttt{trend\_rule} detector raises gradual-degradation $F_1$ from
        $0.000$, the score of every stateless detector on that pattern, to \BManFone{}
        (recall \BManRecall{}, precision \BManPrecision{}). Slow, sustained drift is exactly the
        failure mode a point-based rule misses. The threshold rule remains the
        deterministic fallback beneath the default, and an Isolation Forest engine
        \cite{liu2008isolationforest} is a selectable alternative. A separate
        threshold-versus-Isolation-Forest sweep, which does not involve the deployed
        detector, shows about \BManAgree{} cell agreement, with the Isolation Forest the more
        aggressive of the two.
  \item \textbf{The deterministic router is the routing contribution.} The deployed
        capacity-aware monotone heuristic holds SLA violations to \BMrlMonoSla{} against
        \BMrlRrSla{} for round-robin closed-loop and passes every monotonicity probe. The
        trained PPO policy \cite{schulman2017ppo,raffin2021sb3} is an honest null result:
        round-robin-equivalent (open-loop mean-reward gap \BMrlPpoReward{}), the worst contender
        closed-loop at \BMrlPpoSla{} SLA violations, and kept dormant in shadow mode. The
        live value comes from the deterministic heuristic over the classical scheduler.
  \item \textbf{The forecaster ships a reliable default with fallbacks in reserve.} The
        deployed \texttt{harmonic\_residual} forecaster records the best accuracy at
        \BMfcMape{} MAPE and lifts downstream SLA attainment by \BMfcSlaGain{}\,pp over the
        reactive baseline. The moving-average model is its deterministic fallback, and an
        ARIMA forecaster \cite{box2015timeseries} of order $(2,0,2)$ is an optional
        alternative that fits out of distribution on these synthetic series and ranks
        worst of the four.
  \item \textbf{The system is thoroughly tested.} Several hundred automated tests span the
        unit, contract, integration, and end-to-end layers, and the benchmark harness
        surfaced the very issues that had to be resolved before the loop could be observed
        closing.
\end{itemize}

Together these establish that SmartLoad's architecture is sound and its control loop
real: the deployed anomaly engine closes the gradual-degradation gap a point-based rule
misses, the deterministic router beats the strong baseline while the learned policy stays
dormant as an honest null result, and the deployed forecaster ships the most accurate
model with fallbacks in reserve. The closed loop is carried by the actuation chain and
the deterministic heuristics, not by any learned model running live.

\section{Lessons Learned}
\label{conc:lessons}

\subsection{Lessons learned}
\label{conc:lessons-learned}

Three lessons recur across the project, each shaping a decision a less careful process
would have made differently.

\paragraph{A deterministic fallback is what makes a learned component safe to deploy.}
Insisting on a classical baseline beneath every model was not a hedge but the enabling
condition. Because the threshold rule, the moving-average forecaster, and the round-robin
scheduler are always present, we could put learned routing and anomaly models into the
live request path without risking production, and measure each engine against its own
floor on a live stack rather than in an offline harness. The fallback turns ``learned
routing is risky'' from a reason not to build the system into a property the system
guarantees.

\paragraph{Building in vertical slices with tests at every layer kept the system
reliable.} We built SmartLoad as vertical slices (data, decision, and control planes),
backing each with unit, contract, integration, and end-to-end tests as it landed. Every
layer was exercised before the next depended on it, so the test suite grew alongside the
code instead of being bolted on at the end. When the benchmark harness later surfaced
real issues, the tests made them quick to pin down and fix.

\paragraph{Pairing each learned engine with a proven baseline gives both safety and a
path to improvement.} Every learned engine ships next to a classical counterpart it can
be measured against: the PPO router \cite{schulman2017ppo} beside round-robin, the ARIMA
forecaster \cite{box2015timeseries} beside the moving average, and the Isolation Forest
detector \cite{liu2008isolationforest} beside the threshold rule. This keeps the system
safe, because the baseline is always there to fall back to, and makes progress visible,
because every engine has a clear quantitative target to improve against on a live stack.

\section{Future Directions}
\label{conc:future}

The delivered scope opens a roadmap whose leading items are the production-readiness gaps
the audit surfaced. The directions below are ordered by leverage on turning the
demonstrated loop into a deployable product, and each builds on what already works.

\paragraph{Build the real cloud and Kubernetes actuation paths.} The cloud and
Kubernetes load-balancer adapters are stubs that raise \texttt{NotImplementedError}
today, leaving the Docker Compose path as the only live actuation backend. The first
production step is to build these paths for real, against a managed load balancer and
Kubernetes endpoints. This is construction work, not a configuration flip.

\paragraph{Add configuration, secret, and model-ops infrastructure.} A deployable service
needs configuration and secret management in place of inline defaults, and a model-ops
retraining pipeline so the learned engines can be refreshed on real traffic rather than
shipped as static artefacts. Both are prerequisites for running the stack beyond a single
demonstration host.

\paragraph{Replace the proxy arrivals signal and add data-plane health checks.} The
forecaster currently reads an upper-band proxy for request arrivals rather than a true
arrivals signal, and the data plane has no first-class health-check surface. Wiring a
genuine arrivals feed and data-plane health checks would harden the loop against
conditions a single benchmark host does not exercise.

\paragraph{Run a multi-run head-to-head and finish the K8s/Helm packaging.} A multi-run
baseline-versus-SmartLoad comparison would produce per-phase deltas with confidence
intervals in place of the single committed runs. Paired with Helm templates and raw
Kubernetes manifests, it unlocks a multi-host evaluation surface and the K8s
HPA-versus-SmartLoad autoscaling comparison \cite{k8shpa} against the cloud-native
baseline. \Cref{fig:conc:k8s} sketches the target topology, which is not the deployment
the system runs on today: the evaluated stack runs under Docker Compose on a single host,
as recorded in \cref{tab:conc:limitations}. In the planned layout each service becomes
its own Deployment, stateful components move to StatefulSets or managed equivalents, and a
Kubernetes Horizontal Pod Autoscaler stands in for the SmartLoad autoscaler so the two
strategies can be measured side by side.

\paragraph{Retrain the learned engines on representative traffic.} The trained router
needs heterogeneous-latency traces in which backend identity correlates with latency
before it can improve on the deterministic heuristic, and the optional ARIMA forecaster
needs in-distribution training before it can compete with the deployed
\texttt{harmonic\_residual} model. With a model-ops pipeline in place, both can be
refreshed and re-evaluated against their deterministic counterparts.

\paragraph{Build the multi-tenant SaaS phase.} A planned Phase-2 turns the single-tenant
middleware into a managed offering: per-tenant isolation, tenant API keys and RBAC,
operator-UI authentication, rate limiting, and an outbound webhook dispatcher. These
build on the current architecture and open the path from middleware to a hosted product.
Because the shipped system is single-tenant, the two designs that follow describe target
behaviour rather than implemented features. \Cref{fig:conc:mt} shows the proposed
isolation model, in which tenant identity is resolved once at the API edge and carried
through every storage write and event channel, and \cref{fig:conc:webhook} shows the
proposed webhook delivery path for customers who cannot subscribe to the internal Redis
bus directly.

\paragraph{Explore additional learned anomaly models.} For temporal patterns that are
only abnormal relative to their context, an LSTM-autoencoder anomaly engine
\cite{su2019omnianomaly} trades a heavier training pipeline for sequence-aware detection
that complements the point-based Isolation Forest.

\section{Closing Remarks}
\label{conc:closing}

SmartLoad set out to make adaptive load management both \emph{proactive} and
\emph{trustworthy}, and it delivers a working middleware that closes a predict-ahead
control loop end to end while keeping a deterministic floor beneath every learned
component, in the spirit of the self-managing systems the field has long argued for
\cite{kephart2003autonomic}. The autoscaling loop is demonstrated, the deployed
\texttt{trend\_rule} detector closes the gradual-degradation gap point-based rules miss
($F_1$ $0.000 \rightarrow{}$ \BManFone{}), the deterministic router beats round-robin in the
live path while the trained policy stays dormant as an honest null result, and the
deployed \texttt{harmonic\_residual} forecaster ships the most accurate model with
fallbacks in reserve. What lies ahead is a production-readiness roadmap rather than a
redesign: real cloud and Kubernetes actuation paths, a configuration and model-ops story,
a true arrivals signal, data-plane health checks, and a SaaS path that grows the
middleware into a managed offering. The architecture is sound, the results are real, and
the discipline that produced the system, namely measure against the production task, keep
a safe baseline, and build in tested slices, is what will carry it forward.
